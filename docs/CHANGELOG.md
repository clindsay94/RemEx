## [2.0.0] — 2026-07-04

### Added
- Remote desktop, Android: **translated remote-desktop preset labels and warning messages to 8 languages** (RemEx-c93). The remote-desktop preset chip labels, warning messages, and resolution scale strings are now translated into Spanish (es), French (fr), Hindi (hi), Indonesian (in), Polish (pl), Portuguese - Brazil (pt-rBR), Turkish (tr), and Ukrainian (uk) to fulfill ship-quality localization. (values-es, values-fr, values-hi, values-in, values-pl, values-pt-rBR, values-tr, and values-uk strings.xml.)
- Remote desktop, Android: **the "PC keys" modifier bar is now independent of the soft keyboard and gained Ctrl** (RemEx-yi8o). Previously the bar only showed alongside the IME (which could cover it) and had no Ctrl button. It now toggles on its own via the toolbar (`pcKeysBarVisible`), stays visible while explicitly opened even after the IME is dismissed, and renders above the IME via `imePadding()`. Shift/Ctrl/Alt/Win are now full latching chips (`ModifierState`: OFF → ARMED (applies to the next keypress only) → LOCKED (held down on the host until cycled back to OFF), `cycleModifier`). Typing a single alphanumeric character while a modifier is armed/locked now sends it as a real chord (Ctrl+C/V/A/Z, etc.) via `sendKeyPress` instead of as literal text; every other edit (multi-character, punctuation, autocomplete) keeps the existing text path unchanged. All 4 new content-description strings are translated across all 8 supported locales. **Known gaps, filed separately:** AltGr is not implemented (RemEx-9krr); an ARMED modifier can silently persist onto an unrelated later keystroke if the very next input isn't a plain single-character insert, e.g. punctuation or autocomplete (RemEx-rimh). (`ModifierState`, `RemoteDesktopViewModel.cycleModifier`/`sendKeyPress`/`releaseAllModifiers`, `RemoteDesktopScreenContent`, `singleCharacterInsertion`, `asciiAlphanumericVirtualKeyCode`.)
- Remote desktop, Android: **quality presets rebuilt to spec — Unlimited / Smooth & Sharp (default) / Balanced / Data Saver / Custom** (RemEx-vj31). The old 3-chip set (Performance/Balanced/Crisp) had labels and semantics that didn't match the product plan and offered no way to hand-tune capture scale. Each preset is now a named `{quality, targetFps, scale}` bundle (`DesktopPreset`, `DESKTOP_PRESET_BUNDLES`): Unlimited (100%/120fps/100% scale — the uncapped technical ceiling, which this capture pipeline can't always sustain, so it carries a persistent "may vary" info caption plus a one-time Snackbar overflow warning shown only the first time it's selected); Smooth & Sharp (95%/120fps/50% scale, new default — the scale that reliably sustains steady 120fps); Balanced (85%/60fps/75% scale); Data Saver (60%/30fps/65% scale). Selecting **Custom** reveals raw quality/fps/scale sliders (a scale slider is new — previously scale was only reachable via presets); selecting a named preset hides them. The preset id persists in DataStore (`desktop_preset` key) alongside quality/fps/scale, so the sheet reopens showing the correct selection instead of re-deriving it from raw numbers (which couldn't distinguish Custom from a coincidental match). Installs upgrading from the old 3-preset system — which have leftover quality/fps/scale but no persisted preset id — resolve to Custom rather than falsely claiming a named preset that doesn't match their actual settings. (`DesktopPreset`, `RemoteDesktopViewModel.applyDesktopPreset`/`selectCustomPreset`, `SettingsManager.RemoteDesktopPreferences`, `RemoteDesktopScreen`.)
- Remote desktop, Linux: **hardware H.264 (NVENC) is now the real steady-state codec on KDE Wayland — ~68 FPS per-monitor streaming, up from 12.5 FPS CPU MJPEG** (RemEx-nadp, RemEx-lq6h). Four pieces landed together: (1) the PipeWire stream now requests an explicit `maxFramerate` range (1–120), without which KWin delivers on a slow damage-driven cadence (~12 FPS) no matter how fast the encoder is; (2) the captured full-virtual-desktop frame is **cropped to the selected monitor** before encoding, so a single 2560×1440 monitor stays under the 4096-px H.264 hardware limit and needs no CPU downscale (the "both screens" 5120×1440 surface still auto-downscales to fit); (3) per-monitor display enumeration on KDE Wayland via `kscreen-doctor` (true geometry + primary), feeding the display selector, with a fresh session defaulting to the primary monitor; (4) monitor selection works mid-session and on any display server because the crop is applied post-capture. Verified end-to-end on CachyOS/KDE: 67–71 FPS H.264 on either monitor, 49–57 FPS on the full dual-monitor desktop. (`pipewire_capture.c`, `LinuxScreenCaptureService`, `LinuxJpegEncoder`, `RemoteDesktopHandler`.)
- Remote desktop, Linux: **drift-free absolute mouse injection through the unified RemoteDesktop+ScreenCast portal session** (RemEx-lq6h). Absolute pointer targets now go through `NotifyPointerMotionAbsolute` on the same portal session that owns the capture stream (stream-relative coordinates, compositor-clamped), replacing the relative-delta emulation whose unclamped virtual tracker desynced permanently on every screen-edge overshoot — the "mouse doesn't clamp" bug. The host additionally clamps every absolute input target to the active capture region (all platforms), so the pointer can never be driven onto a monitor the remote user isn't viewing. The relative-delta path remains as an automatic fallback when no capture session is active. Verified live: exact landings, right/bottom-edge clamp, and left-edge confinement to the streamed monitor. (`LinuxPortalRemoteDesktopSessionService.TryNotifyPointerMotionAbsolute`, `LinuxCaptureSessionLifetime.TryInjectPointerMotionAbsolute`, `LinuxInputSimulationService`, `RemoteDesktopHandler.ClampToActiveBounds`.)
- Linux: **RemEx now auto-starts at login** — the Linux equivalent of the Windows Task Scheduler logon task (RemEx-aep.7). `client-install.sh` writes an XDG autostart entry (`~/.config/autostart/remex-client.desktop`, `Exec=… --minimized`, `X-GNOME-Autostart-enabled=true`) so the agent comes up minimized to the tray at sign-in, ready for the phone to connect; uninstall removes it, and it is the **same file** the in-app Settings > "Launch at login" toggle manages, so the two stay in sync. `StartupRegistrationService` now mirrors the installed launcher (prefers the per-user `~/.local/share/applications/remex-client.desktop`, falls back to the system copy, then to a generated entry branded `Name=RemEx` / `Icon=remex` to match). The `.desktop` generation strips CRLF (the templates live on a shared Windows/Linux drive), so entries pass `desktop-file-validate`. The headless SYSTEM service (`remex-host.service`, for logged-out power commands) is intentionally kept — it serves a different purpose than the interactive user-session autostart. (`installer/linux/client-install.sh`, `StartupRegistrationService`.)
- Linux: **runtime-validated the P0/P1 security file permissions on CachyOS** (RemEx-lr9) and added Linux regression tests asserting `cert.pfx` and `paired_clients.json` (which holds reconnect secrets) are written `0600`, and that mDNS advertises only real interfaces — excluding Tailscale/CGNAT (`100.64.0.0/10`), loopback, and link-local. Confirmed the former named-pipe IPC ACL surface (IPC-1/6) is gone (`System.IO.Pipes` imported nowhere), so that check is obsolete. (`CertificateServiceTests`, `PairedClientRegistryTests`, `MdnsInterfaceFilterTests`.)
- Remote desktop: **binary cursor-position protocol** (opt-in capability `supportsBinaryCursor`). High-frequency cursor position (60–90×/s) now travels as a fixed 32-byte binary packet (`DesktopCursorBinaryEnvelope`, magic `"RDXC"`) over the existing `/ws/desktop` binary channel — demultiplexed from H.264 frames by magic (distinct from a NAL start code and the `"RDXF"` frame envelope) — instead of a JSON `desktop_cursor_state` message. This removes per-message JSON string allocation on the .NET host and, on Android, the JNI re-serialization to a JSON string *plus* the `JSONObject` parse: the packet crosses JNI as a `byte[]` and is parsed with `ByteBuffer`, cutting GC churn / micro-stutter on both sides. X/Y are signed (negative virtual-desktop monitors are representable). The cursor *shape* still travels as JSON (rare, large). Additive and capability-gated — **no `protocolVersion` bump**; older hosts/clients stay on the JSON path. NativeAOT-safe (`BinaryPrimitives`/spans). Requires an Android rebuild (the `Remex.Core`/`libRemexCore.so` JNI layer changes). (`DesktopCursorBinaryEnvelope`, `DesktopClientCapabilities.SupportsBinaryCursor`, `RemoteDesktopHandler.SendCursorBinaryAsync`, `RemexDesktopClient`, `AndroidNativeExports`, `RemexClientManager`, `RemoteDesktopViewModel`.) (RD-E)
- Remote desktop: **opt-in "keep session unlocked while connected"** (off by default, Windows). When enabled, RemEx keeps the signed-in session usable for the life of a remote-desktop connection — reconnecting a disconnected/locked session to the console (via `tscon`, run by the Session-0 service) so input works even after a Microsoft "Windows App" (RDP) client disconnects and locks it, holding off idle-lock, and re-locking (disconnecting) the session when the last client disconnects. It is security-sensitive — while engaged it unlocks the PC without a password — so it stays disabled unless explicitly turned on, engages only for an authenticated remote-desktop stream, and audit-logs every unlock/re-lock. Currently enabled via a `ProgramData\RemEx\keep-session-unlocked.flag` file containing `1`; an in-app toggle with a security warning is a follow-up. Pure decision logic (`SessionGuardPolicy`) is unit-tested. An **in-app Settings toggle** (Windows-only, off by default) now turns it on/off, with a prominent, fully-localized (8-language) security warning shown while enabled; the toggle writes the `ProgramData` flag via a new `ISessionKeepUnlockedService`. Live unlock/re-lock still requires on-PC verification. (`IInteractiveSessionGuard`, `WindowsInteractiveSessionGuard`, `SessionGuardSettings`, `ISessionKeepUnlockedService`, `SettingsViewModel`, `SettingsView`, `RemoteDesktopHandler`.) (RemEx-l6o)
- Remote desktop now **confines the host cursor to the streamed display** while a single monitor is being streamed, so the pointer can't wander onto another monitor the remote user can't see (where it would just disappear). Implemented host-side via Win32 `ClipCursor`, re-applied on each cursor tick (Windows releases the clip on display/desktop/foreground changes) and released when streaming stops, cancels, or the client disconnects. No-op when streaming the full virtual desktop, and on Linux. (`IInputSimulationService`, `WindowsInputSimulationService`, `RemoteDesktopHandler`.)
- Remote desktop, Android: **fullscreen overlay now includes Start and Stop stream controls** (RemEx-klq). The fullscreen mode previously exposed Settings and Exit Fullscreen but no way to start or stop the stream — forcing users out of immersive mode just to restart a dropped connection. A **Play** button (disabled while a connection is in progress) and a **Stop** button (styled with `errorContainer` colors for quick recognition) are now in the fullscreen action row. (`RemoteDesktopScreen`.)
- Remote desktop now **pans to follow the cursor while zoomed in**: when you zoom past 1× and the host cursor nears the edge of the view, the picture glides to keep it on screen (edge-deadzone tracking that mirrors the Microsoft Windows App), instead of letting the cursor disappear off the edge. With this in place, the remote-desktop screen **no longer forces landscape** — it rotates with the device like the rest of the app. (`PanFollowCalculator`, `RemoteDesktopScreen`.)
- Remote desktop now defaults to **120 FPS** streaming on a fresh install across both the Windows/Linux host (`DesktopConfig`, `RemoteDesktopHandler`) and the Android client (`RemoteDesktopConfigState`, `SettingsManager` DataStore defaults, connection-screen slider). High-refresh phones get the full frame rate with no manual settings change.
- Remote desktop, Android: **PC-keys bar gained AltGr and an expandable F-key/nav-key grid** (RemEx-9krr, RemEx-bct). AltGr is a fifth latching modifier chip (`VK_ALTGR = 165`/`VK_RMENU`) alongside Ctrl/Alt/Shift/Win, following the same ARMED/LOCKED cycle and chord-wrap as the existing four. A new expand chevron on the compact bar reveals a `FlowRow` grid of F1-F12 plus Home/End/PgUp/PgDn/Insert, routed through the same plain keypress path the existing utility keys use — an armed/locked modifier wraps these for free (e.g. Ctrl+Home) with no new chord logic. This closes out the remaining scope of the deferred RemEx-bct special-keys-toolbar ask; the toggle buttons, latching modifiers, and chord routing it also called for had already shipped via RemEx-yi8o. F1-F12 labels are literal (never localized by any keyboard vendor); the 5 nav keys + AltGr + the chevron got real content-description strings across all 8 supported locales. The modifier-wrap decision was extracted from `RemoteDesktopViewModel.sendKeyPress` into a pure `computeChordApplication` (new `RemoteDesktopChordApplication.kt`), covered by `RemoteDesktopChordTest`. (`RemoteDesktopViewModel`, `RemoteDesktopScreen`, `RemoteDesktopChordApplication.kt`.)
- Remote desktop, Windows: a **Windows.Graphics.Capture (WGC) screen-capture backend**, now the preferred per-monitor capture path ahead of DXGI Desktop Duplication. The host tries capture backends in a **WGC → DXGI → GDI** ladder, so the modern, driver-robust WGC API replaces hand-rolled Desktop Duplication for monitor capture — targeting the recurring DXGI bug class (driver-wedge / black screen `RemEx-crk`, `DXGI_ERROR_ACCESS_LOST`, cursor-only freeze `RemEx-ltd`) **without any change to the wire protocol, H.264 encoder, Android client, or pairing**. WGC captures cursor-less (`IsCursorCaptureEnabled = false`), so the existing GDI cursor-shape streaming continues to drive the remote cursor, and the yellow capture border is suppressed (`IsBorderRequired = false`, via `IGraphicsCaptureSession3` so it no-ops cleanly on older Windows). A machine-wide HKLM toggle — `HKLM\SOFTWARE\RemEx\Capture\Backend` = `Auto` (default) \| `Wgc` \| `Dxgi` \| `Gdi` — lets an operator pin a problematic GPU to DXGI/GDI, or A/B WGC vs DXGI, with no redeploy; it fails open to `Auto` so a bad value can never disable capture. The WinRT-touching code is isolated in a new Windows-only `remex.agent.windows` project (TFM `net10.0-windows10.0.19041.0`) referenced **only on Windows** behind the `WGC_CAPTURE` constant, so the Linux build is completely unaffected. WGC, like DXGI, requires the interactive session (not Session 0) and a GPU, so it isn't CI-testable; coverage stays at the `IScreenCaptureService` seam plus the new HKLM-preference parse tests, with the real validation a manual interactive matrix. The shared encoder-dimension helper `CaptureScaling` moved from `remex.agent` to `Remex.Core` so the new project shares the one formula. (`IWgcCaptureSource`, `WgcDesktopCapture`, `CaptureBackendPreference`, `WindowsScreenCaptureService`, `HostBootstrapper`.) (RemEx-g6r)

- **Linux install is now a single `remex-agent` package — full parity with the Windows single-app model (RemEx-u0oc).** `installer/build-linux.sh` produces one `remex-agent-vX.Y.Z-linux-x64.tar.gz` (the old `remex-client`/`remex-host` pair wrapped the same consolidated `Remex.Agent` binary twice); `client-install.sh` was renamed to `agent-install.sh` (shipped in the package as `install.sh`) and installs to `~/.local/share/remex-agent` with a `remex-agent` launcher symlink and a `remex-agent.desktop` menu + XDG autostart entry. The installer is now also the **upgrade/repair path**: it removes the legacy `remex-host` root systemd service and `remex-client` user install, and migrates a root-owned `/var/lib/remex/cert.pfx` (left behind by the old root service — it bricked every non-root run because the brick canary correctly refused to regenerate) into the per-user store **unchanged**, so SPKI-pinned pairings survive. On the code side, the Linux cert path is now per-user (`~/.local/share/Remex/cert.pfx`, beside `paired_clients.json`) with a one-time, SPKI-preserving auto-migration from `/var/lib/remex` (`CertificateService.ResolveNonWindowsCertificatePath`, unit-tested incl. the unreadable-legacy canary case); the read-side brick-canary message is platform-aware (the old text told Linux users to "restart elevated", which would have created *more* root-owned state); and `StartupRegistrationService` manages `remex-agent.desktop` with a one-time startup migration of legacy `remex-client.desktop` autostart entries (`Program.cs`), preventing double-launch or a stale pre-rename binary starting at login. `build-installer.ps1` dropped the obsolete Linux `-SkipClient`/`-SkipHost` switches; `build-linux.sh` warns-and-ignores the old flags. `docs/LINUX_INSTALL.md` was rewritten as a plain-English beginner guide matching the real install (incl. the cert-repair and double-autostart troubleshooting entries); `docs/ARCHITECTURE-HOST.md` is marked superseded. This supersedes the RemEx-aep.7 note above that the systemd service was "intentionally kept". (`installer/build-linux.sh`, `installer/linux/agent-install.sh`, `installer/linux/remex-agent.desktop`, `CertificateService`, `StartupRegistrationService`, `Program.cs`.)
- **Renamed `scripts/install-service.ps1` → `scripts/autostart-remex.ps1` (RemEx-67x).** The script has not created a Windows Service since RemEx-aep — it registers the elevated Task Scheduler logon task and removes any leftover `RemexHost` service. The old name implied a service still existed and was misleading; all references were updated (`installer/RemEx.iss`, `StartupRegistrationService`, `fix-host-install.ps1`, `BUILDING.md`, `CLAUDE.md`, `AGENTS.md`). No behavior change — same actions (`Install`/`Uninstall`/`Status`/`Start`/`Stop`).
- **RemEx is now a single elevated interactive-session app — the Windows Service is gone (RemEx-aep).** The PC side previously ran as a LocalSystem **Session-0 Windows Service** that spawned a separate interactive GUI host and bridged commands/input across the session boundary. A Session-0 service structurally cannot capture the interactive desktop or inject input into it, and a directly-launched host ran at *medium* integrity, so Windows UIPI silently dropped its input into elevated windows — the two root causes of "the host won't stream" and "the cursor is unusable in an elevated window". `remex.agent` now runs as **one process inside the signed-in user's session, always elevated** (`requestedExecutionLevel=requireAdministrator` in `app.manifest`), **auto-started by a Task Scheduler logon task** (`scripts/autostart-remex.ps1` registers task `RemEx`, `LogonType=InteractiveToken`, `RunLevel=Highest`) so it starts elevated at sign-in with **no UAC prompt**. Elevation is load-bearing: an elevated token keeps FullControl over the machine-wide `cert.pfx` / `paired_clients.json` (ACL = LocalSystem + Administrators, inheritance disabled), so **existing pairings survive with no re-pair** — a non-elevated start would get Administrators as deny-only, fail to read the cert, and brick every SPKI-pinned pairing. `CertificateService` gained a brick canary (logs Critical and refuses to regenerate when an existing `cert.pfx` is unreadable). The in-app "Launch at login" toggle is now backed by the scheduled task; the installer drops the old HKCU Run-key (which would start a competing medium-integrity instance). Pre-login remote control is intentionally dropped (the task fires after interactive logon). Linux gets a follow-up (systemd user service). (`app.manifest`, `autostart-remex.ps1`, `installer/RemEx.iss`, `StartupRegistrationService`, `CertificateService`.)
- **Local IPC collapsed to in-process DI (RemEx-aep).** With the UI and host in one process, the `RemExLocalIPC` named pipe and `LocalIpcServerService` were pure cross-process indirection. The desktop adapters (`IpcClientCommandService`, `IpcWakeOnLanService`, `IpcPairingPinQueryService`, and the app-launcher) now resolve the real host services straight from the embedded host's DI container via a new `EmbeddedHostServiceLocator`; the obsolete two-process "server vs client" mode in `CommandModeContext` (a `Global\RemExServiceMutex` arbiter + a duplicate network listener) is removed. The "Windows Service Management" section of Settings is gone (the launch-at-login toggle remains). 8338 ingress is untouched.
- **Session guard reduced to keep-awake (RemEx-aep).** The interactive session guard no longer runs the `tscon`/`WTSDisconnectSession` reconnect-and-re-lock dance (which only made sense for a Session-0 service resuming an orphaned RDP session, and would lock the very session RemEx now lives in). It is now ref-counted `SetThreadExecutionState` keep-awake only; the "keep session unlocked" toggle keeps the screen awake while a client is connected.
- Remote desktop, Windows: the per-frame capture→encode conversion **no longer routes through `System.Drawing`/GDI+ on the hot path** — the real cause of a ~30 FPS ceiling that hardware NVENC was wrongly blamed for. Every capture backend (WGC/DXGI/GDI) previously wrapped each frame in `System.Drawing.Bitmap` objects and ran a GDI+ `Graphics.DrawImage` software blit, then a separate `LockBits`+`Marshal.Copy` into a fresh multi-MB `byte[]` — every frame. When no resample is needed (capture `scale` 1.0), the new `BgraFrameConverter` reads the mapped staging texture straight into a tightly-packed buffer with a single row-wise `Marshal.Copy` (honoring the GPU row stride) — no Bitmap, no blit. The downscale path (`scale < 1`) keeps GDI+'s native bilinear resampler (a scalar managed bilinear would be slower); GPU-side scaling is a measured follow-up. **For maximum FPS on a capable GPU, capture at full resolution (`scale 1.0`) and let the phone downscale for display** (NVENC handles full res easily; the new fit-to-height framing downscales on the phone). Output byte-count is asserted to equal the encoder's `-s WxH` input (a mismatch makes NVENC emit 0 frames) and unit-tested. (`BgraFrameConverter`, `WgcDesktopCapture`, `DxgiDesktopCapture`.) (RD-C)
- Remote desktop: the **cursor-position stream now paces at a true ~90 Hz**. It used `Task.Delay(11)`, which rounds up to the ~15.6 ms Windows OS timer floor (~64 Hz, missing the target). The video-frame loop and the cursor loop now share one `PrecisionPacer` (the hybrid coarse-sleep + `Thread.SpinWait` pacer), so cursor cadence and frame pacing have a single, regression-guarded source of truth. (`PrecisionPacer`, `RemoteDesktopHandler`.) (RD-A1)
- Remote desktop, Android: the remote screen now applies **orientation-aware initial framing** on connect and on monitor switch (RemEx-2i5). In **landscape** phone orientation the view opens at 1× zoom, showing the whole desktop (pinch to zoom in); in **portrait** orientation the view fits to the phone's height so the stream fills vertically and the user pans left/right to traverse a wide host display. A `lastFitKey` (encoding the active display token and phone orientation) ensures the fit fires once per `(display, orientation)` pair and re-fires automatically on monitor switch or phone rotation. Manual pinch/pan after the initial fit is preserved. (`RemoteDesktopScreen`.) (RemEx-2i5)
- Remote desktop, Android: the cursor overlay's animated position is now **read in the Compose draw phase, not composition**, so the ~90 Hz cursor spring redraws the overlay without recomposing the screen subtree every animation frame (lower CPU/battery/thermal). The pan-follow deadzone epsilon is now density-scaled (was a hardcoded `0.5f` → sub-pixel jitter on high-DPI panels at high zoom); the accelerated pan-follow glide is unchanged. (`RemoteDesktopScreen`.) (RD-B, RD-A2)
- **Project rename (RemEx-bcf):** all project folders, `.csproj` files, and solution entries are now lowercase — `remex.core`, `remex.agent` (was `RemEx.Host`), `remex.agent.windows` (was `RemEx.Host.Windows.Capture`), `remex.desktop` (was `Remex.Client`), `remex.agent.tests`, `remex.desktop.tests`, `remex.core.tests`, `remex.agent.native.linux`, and `remex.android`. C# namespaces and output assemblies move with them: `Remex.Host` → `Remex.Agent` and `Remex.Client` → `Remex.Desktop` (the host binary is now `Remex.Agent.exe`), while `Remex.Core` and the Android JNI library `libRemexCore.so` are unchanged. Runtime/install identities are deliberately preserved so existing installs keep working: the Windows service name `RemexHost`, the systemd unit `remex-host`, the IPC pipe `RemExLocalIPC`, the mDNS `_remex._tcp` type, the `RemEx` product/installer brand, and the `UserSecretsId`.
- Project `README.md` rewritten from a one-line stub into a comprehensive, visually polished landing page — hero/badges, "What's New in 2.0" matrix, feature tour, a color-styled Mermaid architecture diagram, protocol/security/theme tables, system-requirements + getting-started + build instructions, a Documentation hub linking the `docs/` set, project layout, and roadmap. It is the entry point new users reach from the RemEx app. Logo stored at the stable `docs/assets/remex-logo.png` path (decoupled from the legacy `remex.desktop/` asset folder).
- Remote desktop cursor now moves **smoothly instead of stepping**: the host streams the cursor position at ~60 Hz (up from 10 Hz; the cursor shape sync and the `ClipCursor` confinement stay throttled to ~10 Hz to avoid hammering the OS), and the Android client animates the cursor overlay toward each received position with a critically-damped spring, snapping on (re)appearance or display switch so it never slides across the screen. (`RemoteDesktopHandler`, `RemoteDesktopScreen`.)
- Remote desktop host frame pacing rewritten to a **hybrid precision wait**: it coarse-sleeps via `Task.Delay` for the bulk of each frame interval, then busy-spins with `Thread.SpinWait` for the final few milliseconds. A bare `Task.Delay` rounds up to the OS timer resolution (~15.6 ms on Windows), which oversleeps an 8.33 ms (120 FPS) interval to ~15.6 ms and capped the achievable rate near 60 FPS. The new pacing is fully localized — no global timer changes (`timeBeginPeriod`) — so it also benefits Linux pacing.
- The two divergent local-IPC stacks are **collapsed into one**: `LocalIpcServerService` over a single `RemExLocalIPC` pipe (one framing, one ACL, one shared pipe-name constant). The redundant `IpcHostServer` / `RemexIPC` newline-protocol server and its duplicate hosted-service registration are removed, with `LaunchApp` folded into the unified command dispatch (cross-session via `IAppLauncherService`). (IPC-4 RemEx-irl; IPC-5 RemEx-qg2 absorbed.)

- Remote desktop, Android: **fullscreen overlay row polish — shared spacing constants, deduped toggle colors, action order reconciled with the windowed toolbar** (RemEx-klq). The fullscreen top-end row (Settings/FPS/Keyboard/PC-keys/Exit/Stop) previously repeated `16.dp`/`8.dp` padding literals and three near-identical `filledTonalIconButtonColors` blocks inline; these are now `FullscreenOverlayEdgePadding`/`FullscreenOverlayIconSpacing` and a shared `toggleIconButtonColors(active)` helper. The row's action order now matches the windowed `TopAppBar` for the actions both share (Keyboard, PC-keys, Settings, fullscreen-exit, Stop/Play); the fullscreen-only FPS toggle is slotted in without disturbing that shared order. Also fixed the fullscreen Settings button's hardcoded `"Settings"` content description to use the existing localized `R.string.cd_settings` (was never translated). **Not done, left as an open finding:** the two rows still have different action *sets* (Reset/zoom is windowed-only, FPS is fullscreen-only) — deciding whether either belongs on both surfaces is a rendering/UX call, not resolved here. (`RemoteDesktopScreen`.)

### Removed
- **The Linux root systemd service (RemEx-u0oc).** Deleted `installer/linux/host-install.sh` and `installer/linux/remex-host.service` — pre-login power commands are a non-goal on Linux exactly as on Windows (RemEx-aep), and the root-run service was the source of the root-owned `/var/lib/remex/cert.pfx` that bricked user-session starts. ### Security
- Pairing endpoints **gated to loopback** (PAIR-5, RemEx-a75): `GET /pairing-pin` and `POST /start-pairing` now reject any non-loopback caller with a `404` (not advertising the endpoint). Previously these disclosed the active pairing PIN — the out-of-band pairing secret — to unauthenticated remote callers, enabling remote takeover. The host tray reads the PIN over local IPC, not HTTP. (`HostBootstrapper`.)
- **PIN brute-force throttle** (PAIR-2, RemEx-lhd): the PIN verification path now counts failed attempts per session and burns the session (forcing a brand-new PIN) after 5 mismatches, the pairing session lifetime is cut from 10 minutes to 2 minutes, and a per-IP sliding-window throttle (`PairingThrottle`) bounds repeated `/start-pairing` attempts. Closes the online-grinding window against a 6-digit PIN. (`PairingService`, `PairingThrottle`, `HostBootstrapper`.)
- **Reconnect proof-of-possession** (PAIR-1, RemEx-3n6): a persisted `clientId` is no longer a bearer credential. At pairing completion the host binds each client to a 32-byte reconnect secret (the ECDH/HKDF session key) in `PairedClientRegistry`; on every reconnect the host sends a random nonce and requires `HMAC-SHA256(secret, nonce)` back, verified with `CryptographicOperations.FixedTimeEquals`, before trusting the connection. Replaying a captured `clientId` without the secret now fails. Added as **new optional handshake messages** (`reconnect_challenge` / `reconnect_proof`) — **no `protocolVersion` bump**; legacy secret-less clients are challenged and must re-pair. Requires a coordinated Android + Host release. (`PairedClientRegistry`, `PairingService`, `PairingHandler`, `PingPongHandler`, Core `PairingClient`/`RemexNativeClient`, `RemexMessage`/`PairingMessages`.)
- **Hardened `paired_clients.json` permissions** (PAIR-4, RemEx-rc4): the registry store now holds reconnect secrets, so after every write it is locked to the service identity only — Unix `0600` (owner read/write) on Linux/macOS and an ACL granting only LocalSystem + Administrators (inheritance disabled) on Windows. (`PairedClientRegistry`.)
- **Authenticated 8338 command channel** (PROTO-1, RemEx-htt): the external TCP command port — which executes shutdown/restart/sleep/lock — previously dispatched after a *server-only* TLS handshake with **zero client authentication**, so any device on the network could power-control the PC. Commands now carry a paired-client `ClientId` validated against `PairedClientRegistry` before dispatch (default-deny, mirroring the `/ws` gate); unauthenticated callers get `Unauthorized` and the connection closes, and the channel **fails closed** when no authenticator is registered. The listener stays bound to all interfaces by design (authenticated-remote — the Session-0 service must serve commands with no user logged in). (`RemexNetworkListener`, `ICommandChannelAuthenticator`, `PairedClientChannelAuthenticator`, `CommandRequest.ClientId`.)
- **8338 flood / slow-loris bounds** (PROTO-2, RemEx-4ky): the command listener caps concurrent connections via a configurable `SemaphoreSlim` (`Remex:CommandMaxConcurrent`, default 16, reject-at-capacity) and applies handshake/read timeouts (`Remex:CommandHandshakeTimeoutSeconds` / `CommandReadTimeoutSeconds`) through linked `CancellationTokenSource`s, so a slow or idle peer can no longer wedge the channel or multiply `MaxPayloadSize` allocations. (`RemexNetworkListener`.)
- **Oversize `/ws` message no longer leaks connection state** (PROTO-3, RemEx-288): a frame exceeding the 4 MB cap previously threw an uncaught `InvalidOperationException` that bypassed cleanup, orphaning the telemetry stream task and leaking file-transfer/pairing state. The serializer drains and returns null on oversize, and the handler's cleanup now runs in a `finally`. (`MessageSerializer`, `PingPongHandler`.)
- **Host private key no longer world-readable** (PAIR-3, RemEx-dta): the TLS PFX is written atomically with restrictive permissions set **before** any key bytes touch disk (Unix `0600`; Windows ACL: LocalSystem + Administrators), closing the TOCTOU window in which a non-admin local user could read the SPKI-pinned private key. (`CertificateService`.)
- **Local IPC pipe locked down + caller verified** (IPC-1, RemEx-m1i): the live `RemExLocalIPC` pipe granted **Everyone** read/write and returned the active pairing PIN (and accepted power commands) to any local user. The `Everyone` ACE is removed — the pipe grants only LocalSystem (FullControl) + Interactive (ReadWrite) on Windows (`0600` owner-only on Linux) — and secret-returning/state-changing commands additionally verify the connected client is the interactive console user via pipe impersonation. (`LocalIpcServerService`.)
- **Bounded IPC accept loop** (IPC-2, RemEx-n6u): the IPC server handles each client on its own task and re-accepts immediately, with a per-connection read timeout, so a hung/silent local client can no longer wedge the PIN/power channel. (`LocalIpcServerService`.)
- **Explicit ACL on the host-control handoff pipe** (IPC-6, RemEx-oj8): the `RemExHostControl` port-handoff pipe carries an explicit DACL (LocalSystem FullControl + Interactive ReadWrite on Windows; Unix perms on Linux) instead of the default — the Session-0 service (LocalSystem) and the HIGH-integrity interactive GUI host run in different security contexts, so this meaningfully tightens the handoff. (`HostControlServer`.)
- **Pairing acknowledgement HMAC compared as raw bytes** (PAIR-6, RemEx-29e): the host now decodes the client's acknowledgement HMAC from base64 and compares the raw fixed-length bytes with `CryptographicOperations.FixedTimeEquals`, failing closed on malformed base64 — instead of comparing the base64 *text* (encoding artifacts) and risking a throw out of the verify path. Mirrors the client side. (`PairingService`.)
- **No crypto/exception detail leaked to the pairing peer** (PAIR-7, RemEx-xk9): a malformed client ECDH key (or any failure on the pairing-complete path) now returns a generic error to the peer — the wrong-PIN message on the complete path so a crypto/parse error is indistinguishable from a bad PIN — with full detail logged host-side only, instead of interpolating `ex.Message` into the peer-facing error. (`PairingHandler`.)
- **Untrusted pointer samples clamped before integer cast** (RD-8, RemEx-q6u): incoming `DesktopPointerSample` coordinates/deltas (network-supplied floats) are validated through a new `CoordinateValidation` helper — non-finite values (NaN/±Infinity) are rejected and values are clamped to the active stream pixel bounds — before the `(int)` cast, so a hostile sample can no longer wrap into an arbitrary `MoveMouse` coordinate. (`CoordinateValidation`, `RemoteDesktopHandler`.)
- **mDNS-discovered host fields validated before URL build** (NSD-6, RemEx-00x): `MdnsDiscoveryService` now rejects an invalid SRV port and a target that isn't a valid IP/DNS name (`Uri.CheckHostName`) before composing the `ws://` URL from untrusted multicast responder data. (`MdnsDiscoveryService`.)
- **8338 `ClientId` requirement documented for external scripts** (PROTO-1 follow-up, RemEx-lbk): `docs/API_CONTRACTS.md` §4 and `docs/SECURITY.md` now accurately describe that every external-script `CommandRequest` on port 8338 must carry a paired `ClientId` (default-deny; unauthenticated senders get `Unauthorized`), replacing the prior inaccurate "same-IP within 24h" description. No first-party client uses 8338, so this is a documentation/integration concern only.
