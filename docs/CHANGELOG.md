## [Unreleased]

- **`AGENTS.md` rewritten lean (647 → 357 lines) with all 2.0-era history archived to `docs/OLD DOCS/AGENTS-2.0-archive.md`.** The frozen 2.0 Release Gate tables, closed-work narratives, and a duplicate machine-managed Beads block are gone from the live file; the durable do-not-regress rules embedded in those narratives (WinRT `FromAbi`/IID marshaling, `PrecisionPacer`/`DuplicationReinitThrottle` routing, `h264_nvenc_bgra`-only GPU encode, sender-scoped `OpenPipeWireRemote`, warm portal session, SurfaceView `Modifier.layout` invariant, and more) are distilled into a new "Carry-Forward Rules" section. ### Fixed

- **The tutorial screen's welcome emoji and body text no longer ignore the in-app font-scale setting.** `TutorialPageContent` overrode two Material typography roles with hardcoded literals (`displayLarge.copy(fontSize = 64.sp)` on the emoji, `lineHeight = 24.sp` on the body), discarding the per-role scaling `typographyForFontFamily(fontFamilyKey, fontScale)` already applies. Both `Text`s now use their unmodified typography roles, so raising the font-scale preference to maximum visibly enlarges both. (`TutorialScreen.kt`; RemEx-ii9c.)
- **The telemetry view-picker cell now announces its selected/unselected state to TalkBack.** `ViewPickerCell` (the mode picker in the sensor-card "change view" sheet) used a plain `clickable`, carrying no semantic role or selected state — screen readers announced it as a generic button regardless of which view was active. It now uses `Modifier.selectable(selected, role = Role.RadioButton, onClick)`, exposing `SemanticsProperties.Selected`, covered by a new Compose UI test (`ViewPickerCellTest`). (`TelemetryViews.kt`; RemEx-xo8b.)
- **The dashboard's first-run coach-mark overlay and its scrim no longer snap on and off at full opacity.** The overlay was mounted with a raw `if`, so its 62%-black scrim flashed in and out instantly on a screen where everything else is spring-animated. It's now wrapped in `AnimatedVisibility` with `fadeIn`/`fadeOut` sourced from `MaterialTheme.motionScheme.defaultEffectsSpec()`, so the scrim (a plain `.background()` draw inside the animated subtree) ramps smoothly instead. (`DashboardScreen.kt`; RemEx-o1dw.)
- **Dashboard cards now spring into their lifted scale on drag instead of snapping to 1.03x in a single frame.** `DraggableDashboardCard` applied the lift via a conditional `Modifier.scale`, so the one gesture the app's own tutorial demos with spring physics didn't actually have any in the real interaction. The scale now comes from `animateFloatAsState` sourced from `MaterialTheme.motionScheme.fastSpatialSpec()`, applied via `graphicsLayer`; drag/pan/pick-up gesture logic is untouched. (`DashboardInteraction.kt`; RemEx-r39j.)
- **The dashboard card pin toggle now has a real 48x48dp touch target.** The clickable `Surface` was explicitly sized to 24dp — half the Material minimum — while sitting on a drag surface where mis-taps also trigger card gestures. It now wraps `.minimumInteractiveComponentSize()` around the existing `.size(24.dp)`, expanding the touch/hit region to 48dp while the visual chip stays 24dp, centered. Covered by a new Compose UI test (`DraggableDashboardCardTest`), run and passing on-device. (`DashboardInteraction.kt`; RemEx-pdj0.)

- **Dashboard cards now ramp their shadow on pick-up instead of jumping 1dp→8dp in a single frame.** Elevation now animates via `animateDpAsState` sourced from `MaterialTheme.motionScheme.fastSpatialSpec()` (a spatial spec, matching the elevation's z-axis nature, distinct from the effects specs used for the sibling border/alpha animations). (`RemoteDesktopScreen.kt`; RemEx-xj83.)

## [2.4.0] — 2026-07-19

### Added

- **PC sensor-card graph types were curated to seven genuinely distinct views, and a value-accuracy bug in the gauges was fixed.** The picker previously offered twelve; five were redundant or weak once rendered side by side and are retired from the menu (enum members kept and remapped so saved layouts load unchanged): **Radial**→Ring (near-identical), **ValueSpark**→Area→Glow (just a line — the value already renders on every card's own plate, so a "value + sparkline" layer adds nothing on PC), **HuePulse**→Glow (flat wash superseded by value-reactive Glow), **Area**→Glow (a second filled-area chart), and **Big Value** (trend-direction only, no magnitude). The seven kept: Bar, Line, Gauge, Ring, LED Meter, Glow, Dual Metric. **Gauge/Ring/LED now fill against the metric's real scale** (percentages 0–100, temperatures 0–100 °C, others 0–peak) instead of the narrow observed min/max band — a steady 19 % CPU load now reads 19 %, not "nearly full with red top segments." **Glow** is value-reactive (accent → warm red as load climbs). **Dual Metric** overlays a real second series (chosen via a searchable picker) and shows an on-card colour **legend** mapping each line to its sensor. (`SparklineControl.cs`, `CanvasView.axaml`, `SensorViewModel.cs`, `SensorGaugeScaleTests.cs` (new, 4 tests); RemEx-km0i.11.)
- **PC cards can overlay a second metric (Dual Metric view) via a searchable picker.** Right-click → "Second Metric" opens a dialog listing every other live sensor with a search filter (a rig can expose hundreds), replacing an unreliable flat context-submenu. The choice persists via `CardState.SecondarySensorId` and resolves to a live view-model for the overlay series. (`SecondMetricDialog.axaml`(.cs) (new), `SensorViewModel.cs`, `CanvasDashboardViewModel.cs`, `CanvasView.axaml`; RemEx-km0i.11.)
- **PC "Auto" view now picks per metric meaning, not just unit string.** A card left on `Auto` resolves its view from the host-stamped `MetricKind` (loads → ring, memory/throughput → value+spark, temps/voltage → line, clock/power → area, fans → bar) and falls back to the old unit-string heuristic only when the kind is `Unknown` — the PC mirror of Android's `bestDisplayModeFor`. (`SensorViewModel.cs`; RemEx-km0i.11.)
- **PC canvas gains a floating multi-select action bar (Pin / Remove / Done).** Ctrl+click cards to select several at once and a bar appears at the bottom of the canvas with the selection count and one-tap group Pin, Remove, and Done — replacing the buried per-card removal path. Group pin and group remove are single undoable operations, routed through the existing `RemoveCardOperation`/undo stack. (`CanvasView.axaml`, `CanvasDashboardViewModel.cs`, `ICanvasOperation.cs`; RemEx-km0i.12.)
- **PC canvas now has a first-visit coach mark.** The first time you open the sensor canvas, a hint card with a curved arrow points at the "Sensors" (add-cards) button and explains dragging, right-click customization, and Ctrl+click multi-select; dismiss with "Got it." A "?" button replays it anytime, and the hint suppresses itself while cards are selected so it never fights the action bar. Seen-state persists per screen in `DashboardProfile.SeenCoachMarks`. (`CanvasView.axaml`, `CanvasDashboardViewModel.cs`; RemEx-km0i.13.)
- **Android Home Base now has its own motion-first coach marks — not a port of the PC's.** On first visit, a **six-step** overlay teaches the dashboard through animated demonstrations: (1) an **animated hold-to-lift** demo — a finger rests on a sample card, shrinks to "grab" it as a ripple blooms, then springs back to size as the card pops up and drags (the gesture with no visual affordance); (2) & (3) **hollow pulsing rings** pixel-anchored (via `onGloballyPositioned`) to the real ⋮ menu and + button so they highlight without covering; (4) an **animated view-picker pop** out of a card's ⊞ grid icon; (5) an **animated multi-select group drag** — a finger taps two cards (each springs to a selected highlight), then the group lifts and drags together; and (6) an **animated hold-to-select → action bar** demo (reshape / pin / remove) showing the select branch of the hold gesture. All motion uses the **Material 3 Expressive** `MotionScheme` spring tokens (bouncy `spatial` springs for movement/scale, gentler `effects` springs for ripple/scrim), driven by `Animatable`s in coroutine loops so each phase — and parallel phases like "finger returns as card pops" — is real spring physics. A **"?" button** in the header replays it anytime (disabled while a group is selected); the overlay auto-suppresses while a card is lifted or a group is selected, and its scrim blocks input so no sheet can open beneath a live hint. Per-step caption placement keeps the panel clear of each hint's target. Seen-state persists via `SettingsManager.dashboardCoachSeen`. Requires `material3` 1.5.0-alpha24 for the `MotionScheme` token API. (`DashboardCoachOverlay.kt` (new), `DashboardViewModel.kt`, `DashboardScreen.kt`, `SettingsManager.kt`, `strings.xml`; RemEx-km0i.10.)

> New user-facing strings for the above were added to the base (English) resources (`Strings.resx` on PC, `strings.xml` on Android); their translation into the other 8 cultures/locales is tracked by RemEx-km0i.16 (localization rollout). Resource fallback shows English for these keys until then.

### Changed

- **Bumped Jetpack Compose `material3` 1.5.0-alpha23 → 1.5.0-alpha24** so the Android coach marks can use the official M3 Expressive `MotionScheme` spring tokens (`fastSpatialSpec`/`slowEffectsSpec`/etc.), which were added in alpha24. No existing code changed; a full release build (incl. `lintVitalRelease`) passes on the new version. (`gradle/libs.versions.toml`; RemEx-km0i.10.)
- **PC sensor cards now bind to telemetry by stable identity, not raw name.** `CanvasDashboardViewModel.ProcessTelemetry` matches an incoming reading to its card by the host-stamped `SensorReading.Id` (falling back to the name for unstamped sensors), the PC mirror of the host's Id/Kind stamping. A sensor the host relabels mid-session keeps its card instead of spawning an orphan, and two same-named sensors (e.g. dual GPUs both "GPU Temperature") stay correctly distinct. Persisted `CardState.SensorId` intentionally stays the name (it also drives the card title and pin key), so this is a runtime-match refinement with no storage migration. (`CanvasDashboardViewModel.cs`; RemEx-km0i.14.)

### Fixed

- **Sharing a file to RemEx ("Send to PC") from another app no longer crashes when RemEx isn't already running.** The Android share sheet can start RemEx's process cold, straight into the share screen, with no prior visit to the in-app File Manager and no running transfer job — so nothing had initialized the shared `FileTransferEngine` singleton. `ShareToPcViewModel.confirmSend()` then enqueued directly into it, dereferencing the uninitialized `queueStore` `lateinit` and throwing "lateinit property queueStore has not been initialized" the moment you tapped Send. The share screen now starts the engine in its `ViewModel` init (idempotent; mirrors `FileTransferViewModel`), so the cold and warm paths behave identically. The intermittency was purely process state: it only crashed when RemEx was cold. Confirmed with an on-device cold-start reproduction and crash-buffer trace. (`ShareToPcViewModel.kt`; RemEx-c2pg.)
- **The "RAM Total" telemetry card no longer sits on "Collecting Data".** Neither producer was emitting a total-memory reading: HWiNFO frequently exposes no "Physical Memory Total" sensor, and the Windows WMI path emitted only used/available/load. The host now always stamps a `RamTotalGb` reading — Windows from `GlobalMemoryStatusEx.ullTotalPhys`, Linux from `/proc/meminfo` `MemTotal` — injected only when no producer already supplied one, so a real HWiNFO total still wins. Verified on-device alongside the `MetricKind` round-trip (RAM/CPU/GPU cards now read real %/GB, not the old `1089.0ms`). (`WindowsTelemetryService.cs`, `LinuxTelemetryService.cs`; RemEx-km0i.3.)

### Removed

- **Retired the deprecated HTTP pairing-PIN endpoints `GET /pairing-pin` and `POST /start-pairing`.** These were the trust-all HTTP surface Google Play's ASI scanner flagged; RemEx-1t0b (2.3.0) moved PIN auto-fetch onto the `/ws` `pairing_pin_request` message — gated by the **identical** `TransportTrust.IsTrustedForPinAutoFetch` check — but kept the HTTP endpoints one release so shipped Android apps ≤2.2.4 (versionCode ≤32) kept working. The fleet is now past that (versionCode ≥33), so the HTTP endpoints are deleted entirely. Remote first-time pairing over Tailscale is unaffected — the `/ws` path carries exactly the same capability. The single Android reference was already a documentation comment (the Kotlin caller was deleted in RemEx-1t0b); no client change is required. (`HostBootstrapper.cs`, `PairingHandler.cs`, `PingPongHandler.cs`, `PairingPinRequestHandlerTests.cs`; RemEx-0xp0.)
- **Deleted the dead `PairingThrottle` class.** Its only call site was inside the now-removed `POST /start-pairing` handler, and it was never registered in DI — `GetService(typeof(PairingThrottle))` always returned `null`, so the per-IP throttle never actually ran. The active pairing brute-force defense is unchanged: `PairingService` still caps failed HMAC attempts at 5 per session with a ~120 s session lifetime. A genuine per-IP cross-session throttle on the `/ws` pairing path is filed as a follow-up. (`PairingThrottle.cs` (removed); RemEx-0xp0.)

### Security

- **The trust-all HTTP PIN surface is now fully gone from the host.** With `GET /pairing-pin` / `POST /start-pairing` removed, the only path that ever discloses an active pairing PIN is the `/ws` `pairing_pin_request` message, which fails closed on any non-loopback / non-Tailscale transport (`TransportTrust.IsTrustedForPinAutoFetch`) and can only *relay* an already-active PIN — it can never create a session. This eliminates the last endpoint an unauthenticated LAN/internet caller could probe for pairing state. (RemEx-0xp0.)

## [2.3.2] — 2026-07-18

### Added

- **The PC Home screen now links to HWiNFO.** A "Get HWiNFO" card sits beside the GitHub and phone-app links and opens HWiNFO's download page. HWiNFO (with Shared Memory Support) is what powers RemEx's detailed PC hardware sensors, so a new user now has a one-click path to the dependency the hardware-monitoring dashboard depends on. Localized across all 9 cultures. (`HomeView.axaml`, `HomeViewModel.cs`, `Strings*.resx`; Dashboard 2.0.)
- **The Android "add card" picker now groups sensors by device.** With a full HWiNFO rig exposing hundreds of readings, the picker shows a section header per device — CPU, GPU, Memory, each drive (`Samsung 980 PRO 2TB [C:]`), Network, Motherboard, Performance — driven by the host's new per-sensor group, so you can find a card instead of scrolling one flat list. (`DashboardScreen.kt`, `DashboardViewModel.kt`; RemEx-km0i.22.)
- **Android telemetry cards now have 10 genuinely distinct views instead of 3 duplicated-looking ones, plus a picker to choose between them.** `TelemetryDisplayMode` grows from 6 values (2 of which rendered pixel-identically) to 11: big value + trend, value + sparkline, ring gauge, true arc gauge, line, area, bar histogram, and three ambient views (hue-pulse tile, LED meter, dual-metric overlay). Tapping a card's view icon now opens a thumbnail grid (`DisplayModePickerSheet`) instead of blindly cycling; each thumbnail renders the real view against the card's live data. `AUTO` is the new default and resolves per-`MetricKind` (`bestDisplayModeFor`), so a fresh or reset card always gets a sensible view for its metric. The curated starter set grows from 3 cards (CPU/GPU/RAM) to 8 (adds RAM total, CPU/GPU temp, and combined network throughput), all seeded `AUTO`. New files `TelemetryViews.kt` (the 10-view catalog + dispatcher + picker sheet) and `TelemetryFormat.kt` (`formatSensor`/`gaugeFraction`/`bestDisplayModeFor`, replacing the old inline formatting and the broken blind `/100` gauge math). The on-disk layout format gains a `{schemaVersion, cards}` envelope with backward-compatible migration from the old bare-array format and old display-mode names. (`DashboardViewModel.kt`, `DashboardScreen.kt`, `TelemetryViews.kt` (new), `TelemetryFormat.kt` (new); RemEx-km0i.4, RemEx-km0i.5, RemEx-km0i.6.)
- **Telemetry and PC-status cards now render a shape per metric category instead of one universal user-picked shape.** CPU cards default to Square, GPU to Slanted, RAM to Oval, temperature to Gem, network to Pill, Wake-on-LAN to Arch, and PC status to a new plain Rounded Rectangle (shape index 24) — each resolved by `DashboardShapes.resolveShapeIndex` with per-card override → legacy class slider → category default precedence, so an explicit user choice is never silently lost. The old universal Clover4Leaf default is retired via a one-time, idempotent, non-destructive migration (`SettingsManager.migrateShapeDefaultsV2`) that only rewrites an absent-or-legacy-clover stored value, never touches saved card layouts, and isn't undo-tracked. The Personalization shape sliders now show "Auto (per category)" instead of a misleading "Circle" when a bucket is unset, and gained a reset-to-default control plus the previously-missing Remote Desktop bucket. (`DashboardShapes.kt` (new), `Theme.kt`, `SettingsManager.kt`, `DashboardScreen.kt`, `DashboardViewModel.kt`, `PersonalizationScreen.kt`; RemEx-km0i.7.)
- **Dashboard cards now support renaming and an optional live-value overlay on chart views.** Real HWiNFO sensor names are often long even truncated (e.g. "AMD Ryzen 9 7950X3D CCD1 Temp…"), so the view picker sheet gained a title field — type a short name, or leave it blank to keep the original. It also gained a "Show live value" switch: Line/Area/Bar charts previously showed only a squiggle with no number at all, which read as broken on a low-variance reading; toggling it on adds a small corner value chip. Both are per-card and additive on the existing layout envelope. (`DashboardViewModel.kt`, `TelemetryViews.kt`, `DashboardScreen.kt`; RemEx-cgiv.)
- **Dashboard cards can now be rearranged without a drag on any card immediately moving it.** A quick drag anywhere on the canvas — including on a card — now pans the board; holding a card for ~0.5s (with haptic feedback) lifts it into a selection, and a floating action bar (Pin/Reshape/Remove/Done) appears for as long as one or more cards are selected. Tapping additional cards while a selection is active adds them to a group move/pin/remove. `DraggableDashboardCard` extracts the per-card gesture handling that used to move a card on any touch. (`DashboardInteraction.kt` (new), `DashboardViewModel.kt`, `DashboardScreen.kt`, `HapticModifier.kt`; RemEx-km0i.9.)
- **PC sensor cards were redesigned for consistency and given three new visualizations.** The title now sits in its own band at the top of the card, and the value+unit render in their *own* `Viewbox` at the bottom on a floating plate — decoupled from the title, so every card's number now renders at a consistent size instead of shrinking whenever the title was long (e.g. "Average Effective Clock"). The sparkline is more prominent (opacity 0.35→0.6, filling the body beneath the title) while the value stays crisp on its plate above it. Three new graph types join the right-click Graph Type menu, each honoring the card's accent color: **Ring** (a bold full ring gauge), **LED meter** (a segmented bar row whose top segments glow red when the reading runs hot), and **Glow area** (a gradient-filled area with a neon top edge). - **PC sensor-canvas cards gain the per-card customization the Android dashboard has — and their titles are readable again.** Each placed hardware sensor now sits under a semi-opaque backing plate so its name reads clearly over the full-card sparkline (previously the title was a dim purple almost the same hue as the line). Right-clicking a sensor now offers: **Color / Preset** (the 8 `SensorCardTheme` palettes, previously defined but wired to no UI so every card was frozen on one low-contrast scheme), **Rename** (inline edit — real HWiNFO names are long, e.g. "AMD Ryzen 9 7950X3D CCD1 Temp…"), and **Show Value Overlay** (hide the number for a clean ambient card, or keep it on the readable plate). New sensor cards also default to **200×150** — a clean multiple of the 50px snap grid — so they tile edge-to-edge without hand-resizing. All settings persist across restart and are localized across all 9 desktop cultures. ## [2.3.1] — 2026-07-14

### Fixed

- **The phone now authenticates the moment it connects — previously nothing worked until you opened the Task Manager page.** The host issues its reconnect challenge lazily, on the first message that carries the phone's client id — and no screen sent one automatically, so every request was rejected with "Pairing required" until the Task Manager page (coincidentally the only screen that talks on open) happened to trigger the handshake. - **Remote desktop no longer starts black until you switch monitors away and back.** The stream's only guaranteed self-contained keyframe was emitted right at stream start — often before the phone's decoder surface existed — and the phone's one compensating keyframe request was swallowed by the host's 5-second anti-reinit-storm cooldown, so the picture stayed black until a monitor switch forced a full restart. ### Fixed

- **File transfer was completely broken in both directions — every upload and download failed with "Peer did not respond," even though the PC side looked perfectly healthy.** The Android client receives every file-transfer control reply through the NativeAOT core (`libRemexCore.so`): the native inbound router (`AndroidNativeExports.OnNativeMessageReceived`) classifies each incoming `/ws` message and hands file messages to the Kotlin layer via the `onFileTransferMessage` JNI callback. That router used a **hand-maintained allowlist that only listed the 2.0-era message types**, so when the 2.1 File Sharing Overhaul (protocolVersion 3) introduced `file_transfer_ready` / `_complete` / `_result` / `_control`, the richer browse responses (`file_volumes` / `_search` / `_metadata` / `_thumbnail_response`), and consent/push, the router **silently dropped every one of them**. The phone would send its `file_transfer_offer`, the host would genuinely accept it and send `file_transfer_ready` back (hence "it works on the PC side"), but the reply never reached the phone's negotiation waiter — which timed out with "Peer did not respond" for 100% of transfers, both upload and download. The router now forwards the **entire `file_*` family** and lets each Kotlin collector filter for the types it handles, so this single choke point can no longer go stale as the protocol grows. This also un-bricks v3 browse (volumes / search / metadata / thumbnails) and the phone-as-file-host path, which were dark for the same reason. (The earlier RemEx-ix8d "zombie socket" work targeted the wrong layer — the binary `/ws/files` channel — and did not fix this.) (`remex.core/Native/AndroidNativeExports.cs`; RemEx-y6x6.)
- **A file pushed from the phone to the PC saved one folder too deep — at `root/name/name` instead of `root/name` (every uploaded file became a folder named after itself).** By protocol an upload's `destRelativePath` is the destination *directory* — the host appends the file name itself via `CombineHostRelative(DestRelativePath, FileName)` — but the Android client was sending the *full* `directory/filename` path (Share-to-PC via `resolveDestRelativePath`, the file-manager via `combinePath`), so the host doubled it into `directory/filename/filename` (confirmed in host logs as `photo.jpg/photo.jpg`). The client now sends the destination **directory only**, matching what the host expects — no host change required. (`remex.android/.../share/ShareToPcViewModel.kt`, `remex.android/.../ui/screens/FileTransferViewModel.kt`; RemEx-y6x6.)
- **A pushed file failed with "Transfer incomplete" even though every byte was sent.** The bulk data (on the `/ws/files` socket) and the `file_transfer_complete` signal (on the `/ws` control socket) are independent connections, so the tiny completion message raced ahead of the still-in-flight data. The host would finalize the transfer against a partial file — host logs showed `file_transfer_complete` processed *before* the first data frame even arrived — tear down the receive session, then reject every subsequent data frame with "No active inbound transfer." The Android uploader now **drains all acknowledgements** before announcing completion: it waits until the host has acked every byte (the host always acks the `Final` data frame, advancing the committed offset to the full size) and only then sends `file_transfer_complete`, so the completion can no longer overtake the data. (`remex.android/app/src/main/java/com/clindsay94/remex/service/FileTransferEngine.kt`; RemEx-y6x6.)
- **The page-title font picker had no visible effect.** `PageTitleFontFamily` was defined as an *own key* in `App.axaml`, and an Avalonia resource dictionary's own keys take precedence over its merged dictionaries — so the live value `ThemeService` wrote into the merged override dictionary was permanently shadowed by the App.axaml default. `ThemeService` now writes the chosen font directly onto the application's root resource (the winning own key), which still raises `ResourcesChanged`, so page titles re-font live when you pick a font. (`ThemeService.cs`; RemEx-aoln.)
- **Remote desktop went black (cursor only) + briefly zoomed when the resolution scale changed mid-session, recovering only after a monitor switch.** The Android H.264 `SurfaceView`/decoder was keyed on the encoded resolution, so the instant the host reported new dimensions (a capture-scale change rebuilds the encoder) Compose tore the live decoder down and built an empty one — which came up mid-GOP and dropped every P-frame until the host's next periodic keyframe or a monitor-switch re-bootstrap. The decoder already adopts a new resolution *in place* via its own SPS-change reconfigure (`maybeReconfigureForNewSps`), feeding the fresh keyframe with no gap, so the resolution is no longer part of the `SurfaceView` key; only the video-box size still triggers a rebuild (an unrelated frozen-buffer-scale guard). This is the underlying fragility that 2.1.1 only *mitigated* by disabling adaptive capture scale — deliberate scale/preset changes now reconfigure seamlessly too. (`RemoteDesktopScreen.kt`; RemEx-x3eb.)
- **A freshly-created H.264 decoder that came up mid-GOP stayed black until the host's next *periodic* keyframe.** When the decoder is (re)built while the stream is mid-GOP — e.g. the video-box (`imageSize`) settle that still legitimately rebuilds the `SurfaceView` — its pre-configure wait dropped the undecodable P-frames without asking for anything, so it rendered nothing until the host happened to emit its next scheduled IDR (up to a full GOP later). It now requests an on-demand keyframe **once** the moment it sees it joined mid-GOP, so it configures from the very next frame; the one-shot guard avoids flooding the host. Removes the one-time black/zoom on the first scale change after connecting. (`H264StreamDecoder.kt`; RemEx-p7fz.)
- **Changing the resolution preset while the desktop was static froze the H.264 stream on the host — the encoder starved in a reinit loop until something on screen changed.** The WGC and DXGI capture backends cache the last converted frame and replay it whenever the desktop hasn't changed, but the cache didn't remember what *scale* produced it: after a preset switch the replay was the *old* scale's buffer size, the stream loop rejected it against the rebuilt encoder's fixed input size and reinitialized the encoder — every frame, each reinit costing ~1s — so on a static desktop the stream shipped almost nothing (measured: 1 access unit in 5 s) until the desktop happened to repaint. Both backends now tag the cached frame with its scale and, when a different scale is requested with no new frame available, re-derive a correctly-sized frame from the retained staging texture — so a preset change on a perfectly still desktop re-streams immediately (measured: 83 access units in the same 5 s window). The lock-contended replay path likewise reports a wrong-scale cache as stale instead of live so it is never fed to the encoder. (`WgcDesktopCapture.cs`, `DxgiDesktopCapture.cs`; RemEx-wmm8.)
- **Remote desktop rendered zoomed-in — magnification tracking exactly 1/scale (Smooth+Sharp 0.5 = most zoomed, Balanced 0.75 = least) — after a preset change, until an unrelated surface rebuild "refreshed" it.** The `SurfaceView`'s producer buffer geometry is pinned once in `surfaceCreated` via `holder.setFixedSize(streamRes)`; since RemEx-x3eb the surface deliberately *survives* a mid-session resolution change (the decoder adopts the new SPS in place), so nothing ever re-pinned it — and on the S24 Ultra's Qualcomm `c2` decoder a stale fixed size is **not** overridden by the codec's decoded geometry, leaving every frame composited at the creation-time scale (old ÷ new resolution ≈ 1/scale zoom). The `AndroidView` now re-pins `setFixedSize` to the current stream resolution on recomposition (a no-op when unchanged), so preset changes render at correct geometry immediately. (`RemoteDesktopScreen.kt`; RemEx-oenj.)
- **Adding or removing a File Transfer shared folder in Settings had no effect on what the phone could actually browse.** The Settings writer (`FileTransferRootSettingsService`) built its config path straight from per-user `%LocalAppData%\Remex`, while the live host (`FileTransferService`) reads the machine-wide `%ProgramData%\RemEx` location via `RemexDataPaths` (where the host runs as the elevated session app and the TLS cert already lives). After the one-time migration the two paths decoupled on Windows, so edits in Settings silently never reached the host. The Settings writer now resolves its path through the **same** `RemexDataPaths.ResolveDirectory` / `TryMigrateWindowsFile` helpers the host uses, so both read and write one file; behaviour off Windows is unchanged. (`FileTransferRootSettingsService.cs`; RemEx-y8xy.)
- **Android file-transfer notification now shows live progress — required for the Play `FOREGROUND_SERVICE_DATA_SYNC` declaration.** The `dataSync` foreground service posted a static "Syncing files…" notification with no visible activity, which does not meet Google Play's "noticeable to the user" bar for a data-sync foreground service. `FileTransferForegroundService` now observes the `FileTransferEngine.queue` `StateFlow` and re-posts an **ongoing determinate notification** — direction glyph + filename (`↑`/`↓`), a moving progress bar, and `percent · file N/M` — quantized to whole-percent and `sample()`-throttled so per-chunk frames never exceed the OS notification rate limit; Negotiating/Verifying show an indeterminate bar. The in-app File Transfer screen already renders the M3-Expressive `LinearWavyProgressIndicator` for the same progress. One locale-neutral format string added (`file_transfer_service_progress`, `translatable="false"`). (`FileTransferForegroundService.kt`, `strings.xml`.)
- **Android file-transfer polish — upload confirmations, a proper properties sheet, and per-item actions in grid view.** Five gaps in the phone file manager: (1) a Share-to-PC **upload/push now posts a completion or failure notification** the same way a download does — previously it finished silently; (2) the **properties sheet shows a loading spinner** while the metadata round-trip is in flight (it used to stay invisible until data arrived) **and a thumbnail preview** for image files; (3) the **icon-grid view gained a per-item overflow menu** (download · properties · rename · delete · pin) — those actions were reachable only in list view; (4) the **copy/move destination picker surfaces browse errors** instead of showing a silent empty folder; and (5) a hardcoded English `"Error: …"` status string is now localized across all 8 languages. (`FileTransferEngine.kt`, `FileTransferViewModel.kt`, `FileManagerSheets.kt`, `FileManagerFileItem.kt`, `FileTransferScreen.kt`, `FileManagerLogic.kt`, `strings.xml` ×9; RemEx-bi5z.)
- **Dashboard "Wake PC" now reports whether the packet actually sent.** The dashboard's Wake-on-LAN action optimistically showed "sent" regardless of the native result; it now parses the `WakePc` JNI response's success flag (mirroring the Remote Control screen) so a failed wake surfaces as a failure snackbar instead of a false confirmation. (`DashboardViewModel.kt`; RemEx-nbfb.)

## [2.0.1] — 2026-07-11

### Added
- Remote desktop: **`encodedWidth`/`encodedHeight` on `desktop_meta` and `desktop_stream_descriptor`** — the true post-scale, even-aligned encoder output size, distinct from the existing `pixelWidth`/`pixelHeight` (unscaled screen size). The Android H.264 `SurfaceView` now sizes itself from these instead, and the host re-advertises them whenever the encoded size changes mid-stream (preset switch, adaptive-scale step). Additive, no `protocolVersion` bump; hosts predating the fields fall back to `pixelWidth`/`pixelHeight`. (`DesktopMeta`, `DesktopStreamDescriptor`, `RemoteDesktopHandler.GetEncodedFrameSize`.)
- Remote desktop: **adaptive H.264 capture scale** (RemEx-eo0f). A new pure, clock-injected state machine (`AdaptiveScaleController`) holds the sharpest capture scale the host can sustain at the target FPS instead of a fixed preset value — starting at the preset's configured scale and stepping up a coarse ladder (0.4/0.5/0.65/0.75/0.85/1.0) when the encoder proves it can keep up (≥98% of target FPS for 5 consecutive ~2s windows with no output drops), stepping straight back down on any encoded-output overflow or two consecutive windows under 90% of target FPS. 5s minimum between changes; a step-up that fails within its own hold period is barred from retrying for 60s (anti-oscillation). Opt-in via the new `DesktopConfig.AdaptiveScale` field (explicit client value wins; default is on for H.264 at `targetFps >= 90`). Android's SMOOTH_SHARP and UNLIMITED presets opt in explicitly; BALANCED/DATA_SAVER/CUSTOM defer to the host's default rule. (`AdaptiveScaleController`, `IH264Encoder.AcceptedInputFrameCount`/`DroppedAccessUnitCount`, `RemoteDesktopHandler`, `RemoteDesktopViewModel.buildConfigJson`.)
- Remote desktop, Android: **always advertise cursor-state/shape/frame-envelope capabilities**, independent of display-target selection — previously the client only sent `clientCapabilities` at all once a display option was resolved, so a fresh connection with no display picker interaction fell back to the legacy fixed-arrow cursor path. `supportsDisplaySelection` (and the paired `desktopProtocolVersion`/`captureMode`) stay gated on a resolved catalog option, since the host rejects an unpaired `SupportsDisplaySelection` advertisement. (`RemoteDesktopViewModel.buildConfigJson`.)

### Fixed
- Build: **`dotnet build`/`dotnet test Remex.sln` failed with XA5300 ("Android SDK directory could not be found") on any machine without the Android SDK configured**, because `remex.core.csproj` unconditionally multi-targeted `net10.0-android` alongside `net10.0`. `net10.0-android` is now only included in `TargetFrameworks` when `ANDROID_HOME`, `ANDROID_SDK_ROOT`, or an explicit `AndroidSdkDirectory` MSBuild property is set (mirroring how `build-remex.ps1` already resolves the SDK dir) — plain solution builds/tests now succeed without Android tooling installed, while `build-remex.ps1`'s Android build path (which always has one of those set) is unaffected. (`remex.core.csproj`.)
- Remote desktop, Windows: **doubled cursor when WGC can't disable its own cursor compositing.** The WGC capture session's `IsCursorCaptureEnabled = false` projection setter was wrapped in a Debug-only try/catch — on failure, WGC silently baked the OS cursor into every captured frame on top of the client's own rendered cursor (shape + position streamed separately), producing a "trail of cursors" smear under constant-QP encoding. Added a COM fallback (`IGraphicsCaptureSession2::put_IsCursorCaptureEnabled`) for projection versions where the setter throws, and a Warning-level log (not Debug) when both paths fail so the doubled cursor is diagnosable from the host log. (`WgcDesktopCapture.TrySuppressCursorCapture`.)
- Remote desktop, Android: **stream stayed cropped until a fullscreen toggle (or other unrelated re-layout) forced a rebuild.** The H.264 `SurfaceView`'s buffer→view content scale freezes at surface creation; if the surface was first created before real desktop metadata arrived (at the 1920×1080 placeholder) or before the encoded size was known, it stayed mis-scaled until something else happened to force a `key()` rebuild. Surface creation is now gated on `desktopMetaReady`, and the surface sizes itself from the new `encodedWidth`/`encodedHeight` fields instead of the unscaled `pixelWidth`/`pixelHeight`. (`RemoteDesktopScreen`.)
- Remote desktop, Windows: **macroblocking/blur on high-motion frames at high FPS.** The H.264 encoders (NVENC/QSV/AMF/x264) ran pure constant-QP with no `-maxrate`/`-bufsize` anywhere, so bitrate scaled unbounded with FPS×motion; when it overran the bounded encoded-output channel, `DropOldest` silently evicted access units mid-GOP, corrupting the reference chain until the next keyframe. Rate control is now quality-anchored VBR/QVBR with a QP-derived `-maxrate`/`-bufsize` ceiling (`FFmpegH264Encoder.ComputeMaxRateBps`/`ComputeBufSizeBps`), GOP now scales with FPS (`ComputeGop`, clamped 30–120) instead of a fixed 60, and output-channel overflow is now detectable (`DropWrite`) and recovers cleanly by dropping until the next IDR and requesting one, instead of forwarding a broken reference chain. VA-API (Linux) keeps its existing CQP rate control pending separate driver validation. (`FFmpegH264Encoder`.)
- Remote desktop, Windows: **cursor shape change (e.g. arrow → I-beam) took up to ~111ms to reach the client.** Shape re-sync previously only ran on the 10Hz "slow tick" alongside position streaming. (`FFmpegH264Encoder`, `RemoteDesktopHandler`.) (RD-1 RemEx-ii3)
- Remote desktop: **unbounded encoder memory growth** when the consumer falls behind is fixed — the encoded-frame queue is a bounded drop-oldest `Channel` and the Annex-B accumulator is capped (reset past 8 MB without an AUD cut, guarding against malformed/desynced input). (`FFmpegH264Encoder`.) (RD-3 RemEx-fs5)
- Remote desktop: the ffmpeg **stderr reader is cancelled and torn down with the encoder**, so it can no longer touch a disposed logger/process or accumulate orphaned reader tasks during encoder-rebuild churn (e.g. dragging the quality slider). (`FFmpegH264Encoder`.) (RD-4 RemEx-aa0)
- Remote desktop: **dropped decoder input frames no longer cause ~1 s of green corruption**, and a desynced decoder recovers. The Android decoder uses `MediaCodec` async-callback mode with a bounded input queue (no silent drops) and requests a fresh keyframe on error/desync; the host implements **real on-demand IDR** (encoder reinit with forced-IDR codec flags) in place of the previous no-op. (`H264StreamDecoder`, `RemoteDesktopViewModel`, `FFmpegH264Encoder`, `RemoteDesktopHandler`.) (RD-2 RemEx-bqc)
- Remote desktop: a **mid-stream host resolution change no longer garbles the picture** — the Android decoder is (re)created from the host-reported pixel dimensions in frame meta (authoritative after the 4096 clamp) and handles `INFO_OUTPUT_FORMAT_CHANGED` / SPS-PPS-on-IDR reconfiguration. (`H264StreamDecoder`, `RemoteDesktopViewModel`.) (RD-5 RemEx-kx4)
- Discovery: **overlapping NSD resolves no longer fail with `FAILURE_ALREADY_ACTIVE`** or leak a pending resolve — the Android resolver serializes resolves with a mutex and is cancellable on both phases (pre-API-34), fixing the race between manual discovery and reconnect self-heal. (`NsdDiscoveryManager`.) (NSD-1 RemEx-a13)
- Discovery: the host **re-advertises mDNS on network change** (DHCP renew / NIC switch / VPN up-down) instead of advertising once at startup, and **advertises on all preferred interfaces** with Linux-aware virtual-interface filtering (`docker`/`virbr`/`tailscale`/`wg`/`veth`), so multi-NIC and Linux hosts stay discoverable on the client's segment. (`MdnsAdvertisingService`.) (NSD-4 RemEx-ngs, NSD-5 RemEx-i8x)
- Local IPC is now a **length-prefixed framed protocol** (4-byte big-endian length, 1 MB cap) shared by the server and every client, so payloads over 8192 bytes and chunked writes parse correctly and oversize frames are rejected before allocation. (`RemExLocalIPC`, `LocalIpcServerService`, IPC clients.) (IPC-3 RemEx-4ic)
- Protocol-version acceptance is now a **single shared policy** (`ProtocolVersionPolicy`) applied consistently to `/ws` and `/ws/desktop`, replacing two divergent ad-hoc checks (`< 2` vs `!= "2"`). (`ProtocolVersionPolicy`, `PingPongHandler`, `HostBootstrapper`.) (PROTO-4 RemEx-4uy)
- Native JNI pairing exports are now **race-free and exception-safe**. `StartPairingNative`/`SubmitPairingPinNative` serialize all transitions of the pairing-session statics under a dedicated lock (kept separate from the high-frequency frame/callback lock) so a concurrent call from a second Java thread can no longer dispose-then-use the active `ClientWebSocket` (`ObjectDisposedException`); their jstring marshalling now runs inside the export boundary guard so a managed throw is caught instead of escaping `[UnmanagedCallersOnly]`; and the frame/string callback paths clear any pending Java exception on an allocation-failure early return so it can't bleed into the next callback on the shared dispatcher env. (`AndroidNativeExports`.) (JNI-4 RemEx-8ay, JNI-5 RemEx-85i, JNI-3 RemEx-ymb)
- Local IPC server: the backoff `Task.Delay` calls in the accept-loop catch blocks are now cancellation-guarded, so service shutdown exits the loop cleanly instead of surfacing a cancelled task from `ExecuteAsync`. (`LocalIpcServerService`.) (IPC-7 RemEx-79h)
- Local IPC client: an **ACL denial is now distinguished from "no server running"** — `RemExLocalIPC.SendCommandAsync` returns a typed permission error (and the legacy PIN query emits a diagnostic naming the exception type) instead of collapsing every failure into a generic `IPC Error`/`null`, so the UI can surface an actionable message. (`RemExLocalIPC`, `IpcPairingPinQueryService`.) (IPC-8 RemEx-b3m)
- Discovery: `ConnectionViewModel.discoverHost()` now **cancels any in-flight discovery before relaunching** (cancel-previous via a tracked `Job`), so overlapping manual + self-heal calls no longer stack NSD resolves or multicast-lock cycles. (`ConnectionViewModel`.) (NSD-3 RemEx-4bb)
- The loopback gate on `GET /pairing-pin` / `POST /start-pairing` now treats a **null `RemoteIpAddress` as non-loopback** (reject with `404`) instead of throwing `ArgumentNullException` inside the handler. (`HostBootstrapper`.) (PAIR-5 follow-up)
- Android build: the Gradle `.so` sync now **rejects a non-AArch64 / non-ELF `libRemexCore.so`** before it is packaged (validates the ELF magic, 64-bit class, and `EM_AARCH64` machine), restricts candidates to the requested configuration with case-insensitive path matching, and tracks the published `.so` as a **content-hashed task input** so an `-NoClean` build re-syncs when the library changes instead of staying `UP-TO-DATE` and packaging a stale `.so`. (`build.gradle.kts`.) (JNI-6 RemEx-hht, RemEx-l79)
- Remote desktop: the on-demand keyframe-request wire type is now the shared typed Core constant `MessageTypes.DesktopKeyframeRequest` instead of a stray host-local literal. (`RemexMessage`, `RemoteDesktopHandler`.) (RemEx-kjq)

### Security
- Pairing endpoints **gated to loopback** (PAIR-5, RemEx-a75): `GET /pairing-pin` and `POST /start-pairing` now reject any non-loopback caller with a `404` (not advertising the endpoint). Previously these disclosed the active pairing PIN — the out-of-band pairing secret — to unauthenticated remote callers, enabling remote takeover. The host tray reads the PIN over local IPC, not HTTP. (`HostBootstrapper`.)
- **PIN brute-force throttle** (PAIR-2, RemEx-lhd): the PIN verification path now counts failed attempts per session and burns the session (forcing a brand-new PIN) after 5 mismatches, the pairing session lifetime is cut from 10 minutes to 2 minutes, and a per-IP sliding-window throttle (`PairingThrottle`) bounds repeated `/start-pairing` attempts. Closes the online-grinding window against a 6-digit PIN. (`PairingService`, `PairingThrottle`, `HostBootstrapper`.)
- **Reconnect proof-of-possession** (PAIR-1, RemEx-3n6): a persisted `clientId` is no longer a bearer credential. At pairing completion the host binds each client to a 32-byte reconnect secret (the ECDH/HKDF session key) in `PairedClientRegistry`; on every reconnect the host sends a random nonce and requires `HMAC-SHA256(secret, nonce)` back, verified with `CryptographicOperations.FixedTimeEquals`, before trusting the connection. Replaying a captured `clientId` without the secret now fails. Added as **new optional handshake messages** (`reconnect_challenge` / `reconnect_proof`) — **no `protocolVersion` bump**; legacy secret-less clients are challenged and must re-pair. Requires a coordinated Android + Host release. (`PairedClientRegistry`, `PairingService`, `PairingHandler`, `PingPongHandler`, Core `PairingClient`/`RemexNativeClient`, `RemexMessage`/`PairingMessages`.)
- **Hardened `paired_clients.json` permissions** (PAIR-4, RemEx-rc4): the registry store now holds reconnect secrets, so after every write it is locked to the service identity only — Unix `0600` (owner read/write) on Linux/macOS and an ACL granting only LocalSystem + Administrators (inheritance disabled) on Windows. (`PairedClientRegistry`.)
- **Authenticated 8338 command channel** (PROTO-1, RemEx-htt): the external TCP command port — which executes shutdown/restart/sleep/lock — previously dispatched after a *server-only* TLS handshake with **zero client authentication**, so any device on the network could power-control the PC. Commands now carry a paired-client `ClientId` validated against `PairedClientRegistry` before dispatch (default-deny, mirroring the `/ws` gate); unauthenticated callers get `Unauthorized` and the connection closes, and the channel **fails closed** when no authenticator is registered. The listener stays bound to all interfaces by design (authenticated-remote — the Session-0 service must serve commands with no user logged in). (`RemexNetworkListener`, `ICommandChannelAuthenticator`, `PairedClientChannelAuthenticator`, `CommandRequest.ClientId`.)
- **8338 flood / slow-loris bounds** (PROTO-2, RemEx-4ky): the command listener caps concurrent connections via a configurable `SemaphoreSlim` (`Remex:CommandMaxConcurrent`, default 16, reject-at-capacity) and applies handshake/read timeouts (`Remex:CommandHandshakeTimeoutSeconds` / `CommandReadTimeoutSeconds`) through linked `CancellationTokenSource`s, so a slow or idle peer can no longer wedge the channel or multiply `MaxPayloadSize` allocations. (`RemexNetworkListener`.)
- **Oversize `/ws` message no longer leaks connection state** (PROTO-3, RemEx-288): a frame exceeding the 4 MB cap previously threw an uncaught `InvalidOperationException` that bypassed cleanup, orphaning the telemetry stream task and leaking file-transfer/pairing state. The serializer drains and returns null on oversize, and the handler's cleanup now runs in a `finally`. (`MessageSerializer`, `PingPongHandler`.)
- **Host private key no longer world-readable** (PAIR-3, RemEx-dta): the TLS PFX is written atomically with restrictive permissions set **before** any key bytes touch disk (Unix `0600`; Windows ACL: LocalSystem + Administrators), closing the TOCTOU window in which a non-admin local user could read the SPKI-pinned private key. (`CertificateService`.)
- **Local IPC pipe locked down + caller verified** (IPC-1, RemEx-m1i): the live `RemExLocalIPC` pipe granted **Everyone** read/write and returned the active pairing PIN (and accepted power commands) to any local user. The `Everyone` ACE is removed — the pipe grants only LocalSystem (FullControl) + Interactive (ReadWrite) on Windows (`0600` owner-only on Linux) — and secret-returning/state-changing commands additionally verify the connected client is the interactive console user via pipe impersonation. (`LocalIpcServerService`.)
- **Bounded IPC accept loop** (IPC-2, RemEx-n6u): the IPC server handles each client on its own task and re-accepts immediately, with a per-connection read timeout, so a hung/silent local client can no longer wedge the PIN/power channel. (`LocalIpcServerService`.)
- **Explicit ACL on the host-control handoff pipe** (IPC-6, RemEx-oj8): the `RemExHostControl` port-handoff pipe carries an explicit DACL (LocalSystem FullControl + Interactive ReadWrite on Windows; Unix perms on Linux) instead of the default — the Session-0 service (LocalSystem) and the HIGH-integrity interactive GUI host run in different security contexts, so this meaningfully tightens the handoff. (`HostControlServer`.)
- **Pairing acknowledgement HMAC compared as raw bytes** (PAIR-6, RemEx-29e): the host now decodes the client's acknowledgement HMAC from base64 and compares the raw fixed-length bytes with `CryptographicOperations.FixedTimeEquals`, failing closed on malformed base64 — instead of comparing the base64 *text* (encoding artifacts) and risking a throw out of the verify path. Mirrors the client side. (`PairingService`.)
- **No crypto/exception detail leaked to the pairing peer** (PAIR-7, RemEx-xk9): a malformed client ECDH key (or any failure on the pairing-complete path) now returns a generic error to the peer — the wrong-PIN message on the complete path so a crypto/parse error is indistinguishable from a bad PIN — with full detail logged host-side only, instead of interpolating `ex.Message` into the peer-facing error. (`PairingHandler`.)
- **Untrusted pointer samples clamped before integer cast** (RD-8, RemEx-q6u): incoming `DesktopPointerSample` coordinates/deltas (network-supplied floats) are validated through a new `CoordinateValidation` helper — non-finite values (NaN/±Infinity) are rejected and values are clamped to the active stream pixel bounds — before the `(int)` cast, so a hostile sample can no longer wrap into an arbitrary `MoveMouse` coordinate. (`CoordinateValidation`, `RemoteDesktopHandler`.)
- **mDNS-discovered host fields validated before URL build** (NSD-6, RemEx-00x): `MdnsDiscoveryService` now rejects an invalid SRV port and a target that isn't a valid IP/DNS name (`Uri.CheckHostName`) before composing the `ws://` URL from untrusted multicast responder data. (`MdnsDiscoveryService`.)
- **8338 `ClientId` requirement documented for external scripts** (PROTO-1 follow-up, RemEx-lbk): `docs/API_CONTRACTS.md` §4 and `docs/SECURITY.md` now accurately describe that every external-script `CommandRequest` on port 8338 must carry a paired `ClientId` (default-deny; unauthenticated senders get `Unauthorized`), replacing the prior inaccurate "same-IP within 24h" description. No first-party client uses 8338, so this is a documentation/integration concern only.
