## [Unreleased]

### Added

- **Both FAQs now tell you how to stop RemEx launching itself at sign-in.** Both already said it "starts automatically at sign-in" without saying how to change that, so a user who wanted RemEx off their startup had no in-app answer and no way to check what it had installed. The new entries (PC `Faq_Q14`, Android `faq_q15`) lead with the switch rather than the plumbing: Settings → "Launch RemEx when you sign in", quoted in each locale exactly as that file ships the label, because `SettingsViewModel.IsLaunchAtLoginEnabled` → `StartupRegistrationService.SetEnabled` is what actually creates and deletes the autostart registration — pointing a non-technical user at Task Scheduler when a toggle exists would be poor guidance. Both mechanisms are still named for anyone verifying or repairing by hand, as the bead required: on Windows a Task Scheduler task literally named `RemEx` (created via `schtasks /Create /TN "RemEx"`, visible under Task Scheduler Library), on Linux an autostart entry at `~/.config/autostart/remex-agent.desktop`. Both entries give the repair step — toggle it off and back on to recreate the registration — and the Android one then closes with the consequence a phone user needs to know: the phone can only reach the PC while RemEx is running, so with autostart off it has to be started on the PC first. Each locale also names its own Settings screen as that file labels it (`Configuración`, `Налаштування`, `Ayarlar`…), matching the sibling pairing entry rather than inventing a synonym. Translated in all 9 files per platform (key parity 1044 PC / 767 Android). (`AboutViewModel.cs`, `FaqScreen.kt`, 9 resx files, 9 `strings.xml`; RemEx-36n4.)
- **Both FAQs now explain why RemEx needs elevated permission, and what to do when that is why the phone will not connect.** Elevation is load-bearing on Windows — a non-elevated `remex.agent` cannot read the machine-wide `cert.pfx`, so every paired phone is refused while still showing as paired — yet the words "administrator", "elevated" and "UAC" appeared nowhere in either FAQ. New entries (PC `Faq_Q13`, Android `faq_q14`) explain that the certificate is stored where nothing else can read it, that this is what stops another program impersonating the PC, and how to recover. The guidance is split per host OS, because the two are opposites: on Windows the fix is to restart RemEx elevated, while on Linux RemEx deliberately runs unprivileged with a `0600` cert in `~/.local/share/Remex`, `sudo` is the wrong move, and the cause is almost always a root-owned `/var/lib/remex/cert.pfx` left by the retired `remex-host` service — so the answer points at re-running the installer, which repairs that automatically, rather than at a raw `chown` on a path that does not exist yet in that state. Translated in all 9 languages on both platforms (key parity 765 Android / 1042 PC). (`FaqScreen.kt`, `AboutViewModel.cs`, 9 `strings.xml`, 9 resx files; RemEx-csfz.)
- **The PC FAQ now explains the "phone suddenly refuses to connect" certificate-pinning failure.** A new entry (`Faq_Q12`, mirroring Android's `faq_a13` from the PC's perspective) covers why the phone refuses after a RemEx reinstall, backup restore, or hardware move — the phone pins this PC's certificate fingerprint at pairing — and walks through the unpair-then-re-pair fix using the QR code or 6-digit PIN. Certificate pinning is the most likely hard failure a user will ever hit, and the PC previously had no user-facing explanation at all. Translated in all 9 languages (key parity 1040). Reviewed by Opus (PASS). (`AboutViewModel.cs`, 9 resx files; RemEx-a6to.)

### Security

- **The Indonesian FAQ told users to pipe a script from the wrong domain into their shell.** `Faq_Q11_Answer` in `Strings.id.resx` gave the Tailscale install step as `curl -fsSL https://scale.com/install.sh | sh` — `scale.com`, not `tailscale.com`. That is a live, unrelated third party's domain, and the instruction pipes whatever it returns straight into `sh`, aimed at a non-technical user following a help page. Corrected to `tailscale.com`, matching what the other eight locales already said; `scale.com` now appears nowhere in the repo. Found while converting that value's line-break escapes (RemEx-mqwx) and fixed inline rather than deferred, since the fix is one token inside bytes already being rewritten and leaving it meant knowingly shipping it. (`Strings.id.resx`; RemEx-mqwx.)
- **The `/ws/desktop` and `/ws/files` channels now require cryptographic proof-of-possession, not bare clientId presence (VULN-2).** These secondary channels — live screen capture + input injection into the always-elevated desktop, and bulk filesystem read/write — gated only on `IsClientPaired(clientId)`, a presence check, not authentication: a `clientId` is an unguessable-but-not-secret identifier. They now perform the same PAIR-1 HMAC-over-nonce handshake the `/ws` control channel already enforces (new shared `ChannelReconnectAuth`): the host issues a fresh 32-byte nonce and services the socket only when the client returns `HMAC-SHA256(reconnectSecret, nonce)` for the presence-checked clientId. Loopback still bypasses; legacy secret-less paired clients must re-pair. Client side: the native `RemexDesktopClient` answers the challenge synchronously on connect (before any stream-control frame, reusing the reconnect secret the `/ws` client already holds — no new JNI plumbing), and the Kotlin `/ws/files` client answers before any binary frame. **This is a coordinated change — the host, `libRemexCore.so`, and the Android APK must be deployed together, and an on-device round-trip (remote desktop + a file transfer succeed; an un-updated client is rejected) is the release gate.** Covered by 6 new host crypto tests. The 8338 external-script command channel is tracked separately (RemEx-ng5z) because its clients are external automation scripts, not the app. (`ChannelReconnectAuth.cs`, `HostBootstrapper.cs`, `remex.core/Native/RemexDesktopClient.cs`, `remex.core/Native/RemexNativeClient.cs`, `FileTransferChannelClient.kt`; RemEx-s032.2.)
- **The unauthenticated `GET /debug/logs` endpoint has been removed (VULN-1, closes the primary auth-bypass chain).** It served up to 3000 buffered in-memory log lines to any network-reachable caller — Kestrel binds `0.0.0.0:5005` with no auth or loopback gate — and those lines retained the live 6-digit pairing PIN (logged at Information) plus full paired `clientId`s in cleartext. An unpaired LAN/Tailnet peer could read the PIN during the pairing window to complete pairing, or harvest `clientId`s to feed the secondary channels. The endpoint is deleted (diagnostics read the buffer in-process via `InMemoryLogSink.GetEntries()`; there was no remote consumer). Independently: the PIN is no longer written to any log sink at all (removed from `PairingHandler` and `PairingService` — it is shown on the host screen only), and `clientId`s are now redacted to an 8-char prefix everywhere they are logged via a new shared `LogRedaction.RedactClientId` helper. (`HostBootstrapper.cs`, `PairingHandler.cs`, `PairingService.cs`, `PairedClientRegistry.cs`, `TransferSessionManager.cs`, `FileTrustService.cs`, `WindowsInteractiveSessionGuard.cs`, new `LogRedaction.cs`; RemEx-s032.1.)
- **`LaunchApp` now enforces an allowlist and rejects network paths (VULN-3).** The `LAUNCHAPP` command passed the client-supplied `TargetPath` straight to `ProcessStartInfo` after only a `Path.GetFullPath` + existence check, so a paired client could launch *any* file — including a remote `\\attacker\share\evil.exe` — as the always-elevated host (admin RCE). `AppLauncherService` now normalizes the path, rejects UNC / `\\` / `//` / mapped-network-drive targets outright (before any other check), and requires the normalized path to match a persisted launcher entry (`ILauncherStorageService.LoadEntriesAsync`) the PC's owner added themselves. Covered by 8 new tests. (`AppLauncherService.cs`; RemEx-s032.3.)
- **A shared root derived from a read-only root now inherits the parent's permissions instead of escalating to full write/delete (VULN-4).** `AddRootFromPathAsync` pinned every new root with `IsWritable/CanRename/CanMove/CanDelete = true` unconditionally, so a paired client could browse a read-only default root (Documents/Desktop/Pictures/Downloads), pick a subfolder, and re-pin it as a fully writable/deletable root — defeating the read-only designation. The derived root now inherits the parent root's capability flags (a read-only parent yields a read-only child); `CanRemoveRoot` stays true as it is a UI-management flag, not a filesystem-write grant. Covered by 2 new tests. (`FileTransferService.cs`; RemEx-s032.4.)
- **The native TLS client now fails closed when no certificate SPKI pin is supplied (VULN-5).** The SPKI-pinning `RemoteCertificateValidationCallback` was installed only `if (!string.IsNullOrEmpty(spkiHash))`; with an empty pin, `SslStream` fell through to the OS trust manager, which the JNI trust-manager overrides force to accept *any* certificate (full MITM). This was latent (shipping callers gate the empty-pin path) but had no fail-closed backstop. Both `RemexNativeClient` and `RemexDesktopClient` now throw before connecting when the pin is null/empty/whitespace, and the validation callback is *always* installed and rejects when no pin is configured — so an empty pin can never reach an accept-any state. NativeAOT-safe (no reflection). Covered by 10 new tests. (`remex.core/Native/RemexNativeClient.cs`, `remex.core/Native/RemexDesktopClient.cs`; RemEx-s032.5.)
- **Residual unauthenticated info-disclosure endpoints trimmed (VULN-6).** `GET /` no longer returns the full remote-desktop diagnostic report (OS, capture backend, capability/failure detail) to anonymous callers — it is now a minimal `{service, status}` handshake, and capabilities reach paired clients over `/ws` as before. The dead `GET /download/apk` endpoint (which served a hardcoded `Z:\` debug-APK path) is deleted. `GET /pairing-qr` was reviewed and exposes only public-by-design data (host id + certificate SPKI hash); no machine name is disclosed. Covered by new endpoint tests. (`HostBootstrapper.cs`; RemEx-s032.6.)

### Changed

- **Twelve host constructors now fail fast with a named `ArgumentNullException` instead of storing a null dependency.** Required non-nullable dependencies were assigned bare (`_logger = logger;`), so a missing DI registration surfaced later as an opaque `NullReferenceException` from wherever the field was first dereferenced — often on a background thread far from the real cause. They now go through `Guard.NotNull` per the CLAUDE.md null-safety convention, which names the offending parameter via `[CallerArgumentExpression]`. Two constructors gain a real robustness win beyond the diagnostics: `RemoteDesktopHandler` and `WindowsDisplayPowerMonitor` now validate *before* starting their long-running input-queue and message-pump threads, so a bad dependency no longer leaks a live thread. Optional nullable parameters are deliberately left unguarded — guarding them would turn an optional dependency into a hard failure, and in one case would have been fatal: `WindowsScreenCaptureService`'s `IWgcCaptureSource? wgc` is passed as literal `null` by the delegating constructor and resolved with `GetService` (not `GetRequiredService`), so guarding it would have crashed host startup on every build without the WGC project. `RemexNetworkListener`'s `certificateService`/`authenticator` are likewise left bare. The two pairing-flow sites (`PairingService`, `PairingHandler`) were done under explicit operator sign-off and are strictly constructor-assignment edits — the handshake, PIN generation and verification, HMAC computation, session lifetime, and brute-force throttle are byte-identical, verified line-by-line against HEAD by an adversarial review specifically tasked with finding a way to brick pairing. No behavior change on any valid startup path; 790 tests green including 51 pairing tests. Reviewed by Opus (PASS, both rounds). (`RemexNetworkListener.cs`, `ExternalNetworkListenerService.cs`, `MdnsAdvertisingService.cs`, `LinuxCaptureSessionLifetime.cs`, `FFmpegH264Encoder.cs`, `WindowsDisplayPowerMonitor.cs`, `DxgiDesktopCapture.cs`, `HostCapabilitiesProvider.cs`, `RemoteDesktopHandler.cs`, `PairingService.cs`, `PairingHandler.cs`, `WindowsScreenCaptureService.cs`; RemEx-2gl8, RemEx-wpfo.)
- **Bold text is now driven by named emphasized typography roles instead of 60+ ad-hoc weight overrides.** The same visual rank used to get a different weight on different screens (`titleMedium` was SemiBold in 6 places, Bold in 3, Black in 1). `typographyForFontFamily` now builds all 15 M3 `*Emphasized` roles with the app's canonical emphasis weight per role (majority-wins from the pre-migration inventory, ties resolved to SemiBold) — built alongside the base roles so they carry the user's font family and in-app scale, which `Typography.copy()` would otherwise silently drop. 63 call sites migrated to the emphasized roles; base roles are untouched, so plain text renders identically. 18 minority-weight sites shift slightly to their role's canonical weight (e.g. the Personalization section headers Black→SemiBold, WAKE PC Bold→SemiBold). Four deliberate literals remain (AC budget ≤5): two telemetry hero values and the connection orb label at display-weight Black, and one link `SpanStyle` — plus three dynamic-weight conditionals (lock-state chip, directory-vs-file rows) that can't be a single static role. Reviewed by Opus (round-2 PASS; round 1 caught three deeply-line-wrapped sites the migration script missed). (`Type.kt` + 21 screen/component files; RemEx-0855.)

### Changed (docs/tooling)

- **Code comments no longer describe a Windows service, a Session-0 host, or a separate desktop client as the current design.** Seventeen sites across `remex.agent`, `remex.core` and `remex.desktop` still presented the pre-2.0 process model as live — a Session-0 command agent paired with a separate GUI host, a LocalSystem service, "the desktop client". That model has been gone since RemEx-aep; there is one elevated process in the signed-in user's session that is both host and UI, and Android is the only client. This matters beyond tidiness: CLAUDE.md exists partly because these comments have repeatedly misled contributors into designing around components that do not exist. Rationale comments kept their history rather than losing it — the reason `cert.pfx` and pairing state live in machine-wide `ProgramData` really *was* the LocalSystem service, and machine-wide storage is still deliberate, so those now read as "originally X, still correct because Y". Three of the seventeen were not comments at all but text shown to the operator, including one that told a non-technical user to *"configure the Windows service to log on as that user"*; those now say plainly that RemEx must be running in a signed-in session and normally starts on its own. The two independent copies of that message — the primary diagnostic and its fallback — were made identical so they can no longer contradict each other. Comments-only otherwise: no code, signatures or behaviour changed. Reviewed by Opus (round-2 PASS; round 1 correctly failed an incomplete sweep, catching a fixed comment whose verbatim twin was left stale and an edit that contradicted a line eight rows above it). (16 files; RemEx-k521.)

- **`AGENTS.md` rewritten lean (647 → 357 lines) with all 2.0-era history archived to `docs/OLD DOCS/AGENTS-2.0-archive.md`.** The frozen 2.0 Release Gate tables, closed-work narratives, and a duplicate machine-managed Beads block are gone from the live file; the durable do-not-regress rules embedded in those narratives (WinRT `FromAbi`/IID marshaling, `PrecisionPacer`/`DuplicationReinitThrottle` routing, `h264_nvenc_bgra`-only GPU encode, sender-scoped `OpenPipeWireRemote`, warm portal session, SurfaceView `Modifier.layout` invariant, and more) are distilled into a new "Carry-Forward Rules" section. (RemEx-79j3.)
- **`CLAUDE.md` no longer instructs agents to read per-project `AGENTS.md` files that don't exist**, points global instructions at the real `~/.claude/AGENTS.md` (there is no global `CLAUDE.md`), and marks `agy`/`agy-splitter` as external tools to verify before use. (RemEx-79j3.)

### Fixed

- **A non-interactive start was labelled "Service PC", and the About page printed the raw wire token.** `Status_ServiceHost` implied RemEx can be installed as a service; it cannot. The branch is reachable though — `HostCapabilitiesProvider` returns `"service"` when `Environment.UserInteractive && SessionId != 0` is false on Windows, the same condition Linux reports as `"headless"` — so this is a detected state, not a shipped mode, and the label was corrected rather than the branch deleted. All nine locales now say the host has no desktop session, keeping each file's existing noun. A second, worse instance surfaced while verifying: `AboutViewModel` interpolated the raw `RuntimeMode` token into the About page, so a non-interactive start displayed the literal untranslated word "service" in every language. The localizing switch already existed in `ConnectionViewModel` but About bypassed it; it is now extracted as `HostRuntimeLabel` and shared, so the mapping exists once instead of once-and-a-bypass. (9 resx files, `ConnectionViewModel.cs`, `AboutViewModel.cs`, `HostCapabilitiesProvider.cs`; RemEx-9z0f.)
- **The Android Unpair button was English in all eight languages.** `connection_unpair` was the raw literal "Unpair" in every locale file. That undercut other work rather than just looking untidy: several pairing-failure and certificate-change messages tell the user to unpair the PC and pair again, and that instruction is unfollowable when the button it names is labelled in a language the user did not pick. Each translation is derived from the term its own file already uses, with the sibling button `connection_action_repair` as the register and length model — `Desemparejar`, `Découpler`, `अनपेयर करें`, `Lepaskan`, `Usuń sparowanie`, `Desparear`, `Eşleştirmeyi kaldır`, `Скасувати спарювання`. - **Eighteen Hindi strings ended with the wrong script's full stop.** `Strings.hi.resx` terminated 18 values with the CJK ideographic full stop `U+3002` instead of the Devanagari danda `U+0964`. Two earlier beads each tripped over a single instance; this was a systematic artifact of however those translations were produced, so all 18 were swept at once — the file now has zero. The Android Hindi file was checked and is clean, so this was PC-only. Two confirmation titles were also brought back into line with the family established by RemEx-v5it: Hindi's delete title moves from `सुनिश्चित` (closer to "ensured") to `निश्चित`, the accurate "sure" the five power titles use; Ukrainian's moves from the infinitive `Видалити` to the verbal noun `Видалення`, matching its own `Вимкнення`/`Перезавантаження` and making the file internally consistent as Polish already was. Key parity 1044. (`Strings.hi.resx`, `Strings.uk.resx`; RemEx-zmmk.)
- **The Android FAQ now names the same 5009 port bound as the PC one.** It said the fallback goes to "the next free port (5006, 5007, ...)" with no upper limit, which made it the vaguer of the two once the PC side was corrected. Only the parenthetical was replaced in each of the nine files — deliberately surgical, because several of these values carry escaped apostrophes and rewriting whole values is what forced two reverts elsewhere. French uses "au plus 5009" and Turkish "5009 dahil" specifically so the inserted text needs no apostrophe escape. Android keeps the detail the PC text omits: `remex.agent` first tries to reclaim the port from a stale instance of itself, so the common case stays on 5005. (9 `strings.xml`; RemEx-xs83.)
- **The PC FAQ understated the port fallback as a single alternative.** `Faq_Q5_Answer` said port 5005 "will fall back to 5006", but `HostBootstrapper.cs:193-195` loops five attempts at `port + attempt`, so the real range is 5005 through 5009. All nine locales now say RemEx tries the next free port — 5006, 5007 and so on, up to 5009 — one changed clause per file, surrounding sentences untouched. The Android FAQ already had this right and additionally notes that remex.agent first tries to reclaim the port from a stale instance of itself, which is real (`StalePortReclaimer.TryReclaim`, guarded to the canonical port), so the common case stays on 5005; Android is now the vaguer of the two for lacking an upper bound and is tracked separately. (9 resx files; RemEx-j5ru.)
- **Failed canvas snapshots were reported in success green.** `SetSnapshotStatus` is the single funnel for that status line, and every message went through it — "Saved to …" and "Copied to clipboard" alongside "Export failed: …", "Copy failed: …" and "Clipboard unavailable" — while the `TextBlock` had one fixed `SystemSuccessBrush`. So a failed export announced itself in the colour reserved for success. The funnel now carries the outcome (`SetSnapshotStatus(message, succeeded: false)` at the three failure sites) and the line is coloured by a class, `SystemSuccessBrush` by default and `SystemErrorBrush` when the last attempt failed. The view model's doc comment claimed it was "called after a successful snapshot export", which its own call sites had always contradicted; it now describes both paths. (`CanvasDashboardViewModel.cs`, `CanvasView.axaml`, `CanvasView.axaml.cs`; RemEx-40x8.)
- **All eight connection status indicators now animate the same way instead of three of them.** Three carried a local `BrushTransition Property="Fill"` and five had none — an inconsistency that was invisible until RemEx-udds, because `Fill` previously held one brush instance whose `Color` was mutated in place, so the transition had nothing to animate and never fired. With `Fill` now swapping brush objects the three came to life and the mismatch became visible. The transition moved into the two shared `Ellipse.status-dot` / `.status-ring` styles (the ring animating `Stroke`), and the three local `Ellipse.Transitions` blocks were deleted — so the colour and its animation are defined in one place, and all eight crossfade over 0.4s on connect, disconnect and theme switch. Net five lines fewer. (`App.axaml`, 3 views; RemEx-adgq.)
- **The connection status dots ignored the theme too, and they were the hardest case.** Six indicators — the sidebar rail, tray flyout, canvas header, Home radar (ring plus two dots), Connection page and Settings — got their green/red from a literal `ConverterParameter=#22C55E|#F43F5E` (or `#4ADE80|#FF6B6B`; the app used two different pairs) passed to `BoolToColorConverter`. A converter parameter is a string, so `DynamicResource` cannot reach it, which is why RemEx-s7n0 could not fix these alongside the other literals. Teaching the converter to resolve resource keys was rejected: a converter evaluates once per binding, so switching theme at runtime would have left the dots painted in the old theme's colours. They now use the conditional-class idiom this codebase already uses for `Classes.nav-item-active` and `Classes.selected` — `Classes.connected="{Binding …IsConnected}"` against four shared `Ellipse.status-dot` / `.status-ring` styles in `App.axaml` whose setters use `SystemSuccessBrush`/`SystemErrorBrush`. That is correct on both axes: the class flips with the connection state and the brush re-resolves on a theme switch. It also collapses the two divergent colour pairs onto one semantic pair. A side effect worth knowing about: three of these ellipses carry a `BrushTransition Property="Fill"`, which never actually fired before — `Fill` was assigned one brush instance and only that instance's `Color` was mutated, so the transition had nothing to animate. Now that `Fill` genuinely swaps brush objects, the 0.4s crossfade runs for the first time, on connect/disconnect and on theme switch. `BoolToColorConverter` is left in place but now has no callers. (`App.axaml`, 6 views; RemEx-udds.)
- **Danger, warning and status colours were hardcoded, so they ignored the theme the user picked — and one security warning had no colour at all.** 18 hardcoded literals across 7 PC views now resolve through theme tokens, plus one unresolvable resource key in an 8th: `#FF4444`/`#FF6B6B`/`#F43F5E` → `SystemErrorBrush`, `#3A1A1A`/`#4A2A2A` (danger button background and hover) → `SystemErrorBackgroundBrush`/`...HoverBrush`, `#FFD93D` → `SystemWarningBrush`, `#4ADE80` status text → `SystemSuccessBrush`, and the command palette's `#22FFFFFF` pointerover → `CardBackgroundHoverBrush`. SolarFlare shows why this mattered rather than being tidiness: its `SystemError` is `#DC2626` and `SystemSuccess` `#16A34A`, tuned for a light surface, so bright dark-theme literals were being painted onto a pale background — the warning yellow in particular was close to unreadable. One new token, `SystemWarningBackgroundBrush`, was added to all four themes to give the warn tint a home, mirroring the existing `SystemErrorBackgroundBrush` (`SystemWarning` at 0.15 opacity). That is deliberately a normalisation rather than a like-for-like swap: `#15FFD93D` is 8.2% alpha, not 15%, so the warn button's tint is now ~1.8× stronger and matches the danger button it sits beside. Every token used is verified defined in **all four** themes, which is the correctness standard available without a visual pass. Separately, a sweep for unresolvable resources found `SettingsView.axaml` colouring `Settings_KeepSessionUnlockedWarning` — the security warning for letting a paired phone control a locked PC — with `{DynamicResource WarningBrush}`, a key defined in no theme and nowhere else in the app. An unresolved `DynamicResource` yields `UnsetValue` silently (unlike `StaticResource`, which throws), so `Foreground` fell through to the inherited body-text colour: the security warning was rendering **visually indistinguishable from the description line above it**, which is worse than being miscoloured. It now uses `SystemWarningBrush`. ### Fixed

- **File transfer was completely broken in both directions — every upload and download failed with "Peer did not respond," even though the PC side looked perfectly healthy.** The Android client receives every file-transfer control reply through the NativeAOT core (`libRemexCore.so`): the native inbound router (`AndroidNativeExports.OnNativeMessageReceived`) classifies each incoming `/ws` message and hands file messages to the Kotlin layer via the `onFileTransferMessage` JNI callback. This also un-bricks v3 browse (volumes / search / metadata / thumbnails) and the phone-as-file-host path, which were dark for the same reason. (The earlier RemEx-ix8d "zombie socket" work targeted the wrong layer — the binary `/ws/files` channel — and did not fix this.) (`remex.core/Native/AndroidNativeExports.cs`; RemEx-y6x6.)
- **A file pushed from the phone to the PC saved one folder too deep — at `root/name/name` instead of `root/name` (every uploaded file became a folder named after itself).** By protocol an upload's `destRelativePath` is the destination *directory* — the host appends the file name itself via `CombineHostRelative(DestRelativePath, FileName)` — but the Android client was sending the *full* `directory/filename` path (Share-to-PC via `resolveDestRelativePath`, the file-manager via `combinePath`), so the host doubled it into `directory/filename/filename` (confirmed in host logs as `photo.jpg/photo.jpg`). The client now sends the destination **directory only**, matching what the host expects — no host change required. (`remex.android/.../share/ShareToPcViewModel.kt`, `remex.android/.../ui/screens/FileTransferViewModel.kt`; RemEx-y6x6.)
- **A pushed file failed with "Transfer incomplete" even though every byte was sent.** The bulk data (on the `/ws/files` socket) and the `file_transfer_complete` signal (on the `/ws` control socket) are independent connections, so the tiny completion message raced ahead of the still-in-flight data. The host would finalize the transfer against a partial file — host logs showed `file_transfer_complete` processed *before* the first data frame even arrived — tear down the receive session, then reject every subsequent data frame with "No active inbound transfer." The Android uploader now **drains all acknowledgements** before announcing completion: it waits until the host has acked every byte (the host always acks the `Final` data frame, advancing the committed offset to the full size) and only then sends `file_transfer_complete`, so the completion can no longer overtake the data. (`remex.android/app/src/main/java/com/clindsay94/remex/service/FileTransferEngine.kt`; RemEx-y6x6.)
- **The page-title font picker had no visible effect.** `PageTitleFontFamily` was defined as an *own key* in `App.axaml`, and an Avalonia resource dictionary's own keys take precedence over its merged dictionaries — so the live value `ThemeService` wrote into the merged override dictionary was permanently shadowed by the App.axaml default. `ThemeService` now writes the chosen font directly onto the application's root resource (the winning own key), which still raises `ResourcesChanged`, so page titles re-font live when you pick a font. (`ThemeService.cs`; RemEx-aoln.)
- **Remote desktop went black (cursor only) + briefly zoomed when the resolution scale changed mid-session, recovering only after a monitor switch.** The Android H.264 `SurfaceView`/decoder was keyed on the encoded resolution, so the instant the host reported new dimensions (a capture-scale change rebuilds the encoder) Compose tore the live decoder down and built an empty one — which came up mid-GOP and dropped every P-frame until the host's next periodic keyframe or a monitor-switch re-bootstrap. The decoder already adopts a new resolution *in place* via its own SPS-change reconfigure (`maybeReconfigureForNewSps`), feeding the fresh keyframe with no gap, so the resolution is no longer part of the `SurfaceView` key; only the video-box size still triggers a rebuild (an unrelated frozen-buffer-scale guard). This is the underlying fragility that 2.1.1 only *mitigated* by disabling adaptive capture scale — deliberate scale/preset changes now reconfigure seamlessly too. (`RemoteDesktopScreen.kt`; RemEx-x3eb.)
- **A freshly-created H.264 decoder that came up mid-GOP stayed black until the host's next *periodic* keyframe.** When the decoder is (re)built while the stream is mid-GOP — e.g. the video-box (`imageSize`) settle that still legitimately rebuilds the `SurfaceView` — its pre-configure wait dropped the undecodable P-frames without asking for anything, so it rendered nothing until the host happened to emit its next scheduled IDR (up to a full GOP later). It now requests an on-demand keyframe **once** the moment it sees it joined mid-GOP, so it configures from the very next frame; the one-shot guard avoids flooding the host. Removes the one-time black/zoom on the first scale change after connecting. (`H264StreamDecoder.kt`; RemEx-p7fz.)
- **Changing the resolution preset while the desktop was static froze the H.264 stream on the host — the encoder starved in a reinit loop until something on screen changed.** The WGC and DXGI capture backends cache the last converted frame and replay it whenever the desktop hasn't changed, but the cache didn't remember what *scale* produced it: after a preset switch the replay was the *old* scale's buffer size, the stream loop rejected it against the rebuilt encoder's fixed input size and reinitialized the encoder — every frame, each reinit costing ~1s — so on a static desktop the stream shipped almost nothing (measured: 1 access unit in 5 s) until the desktop happened to repaint. Both backends now tag the cached frame with its scale and, when a different scale is requested with no new frame available, re-derive a correctly-sized frame from the retained staging texture — so a preset change on a perfectly still desktop re-streams immediately (measured: 83 access units in the same 5 s window). The lock-contended replay path likewise reports a wrong-scale cache as stale instead of live so it is never fed to the encoder. (`WgcDesktopCapture.cs`, `DxgiDesktopCapture.cs`; RemEx-wmm8.)
- **Remote desktop rendered zoomed-in — magnification tracking exactly 1/scale (Smooth+Sharp 0.5 = most zoomed, Balanced 0.75 = least) — after a preset change, until an unrelated surface rebuild "refreshed" it.** The `SurfaceView`'s producer buffer geometry is pinned once in `surfaceCreated` via `holder.setFixedSize(streamRes)`; since RemEx-x3eb the surface deliberately *survives* a mid-session resolution change (the decoder adopts the new SPS in place), so nothing ever re-pinned it — and on the S24 Ultra's Qualcomm `c2` decoder a stale fixed size is **not** overridden by the codec's decoded geometry, leaving every frame composited at the creation-time scale (old ÷ new resolution ≈ 1/scale zoom). The `AndroidView` now re-pins `setFixedSize` to the current stream resolution on recomposition (a no-op when unchanged), so preset changes render at correct geometry immediately. (`RemoteDesktopScreen.kt`; RemEx-oenj.)
- **Adding or removing a File Transfer shared folder in Settings had no effect on what the phone could actually browse.** The Settings writer (`FileTransferRootSettingsService`) built its config path straight from per-user `%LocalAppData%\Remex`, while the live host (`FileTransferService`) reads the machine-wide `%ProgramData%\RemEx` location via `RemexDataPaths` (where the host runs as the elevated session app and the TLS cert already lives). After the one-time migration the two paths decoupled on Windows, so edits in Settings silently never reached the host. The Settings writer now resolves its path through the **same** `RemexDataPaths.ResolveDirectory` / `TryMigrateWindowsFile` helpers the host uses, so both read and write one file; behaviour off Windows is unchanged. (`FileTransferRootSettingsService.cs`; RemEx-y8xy.)
- **Android file-transfer notification now shows live progress — required for the Play `FOREGROUND_SERVICE_DATA_SYNC` declaration.** The `dataSync` foreground service posted a static "Syncing files…" notification with no visible activity, which does not meet Google Play's "noticeable to the user" bar for a data-sync foreground service. `FileTransferForegroundService` now observes the `FileTransferEngine.queue` `StateFlow` and re-posts an **ongoing determinate notification** — direction glyph + filename (`↑`/`↓`), a moving progress bar, and `percent · file N/M` — quantized to whole-percent and `sample()`-throttled so per-chunk frames never exceed the OS notification rate limit; Negotiating/Verifying show an indeterminate bar. The in-app File Transfer screen already renders the M3-Expressive `LinearWavyProgressIndicator` for the same progress. One locale-neutral format string added (`file_transfer_service_progress`, `translatable="false"`). (`FileTransferForegroundService.kt`, `strings.xml`.)
- **Android file-transfer polish — upload confirmations, a proper properties sheet, and per-item actions in grid view.** Five gaps in the phone file manager: (1) a Share-to-PC **upload/push now posts a completion or failure notification** the same way a download does — previously it finished silently; (2) the **properties sheet shows a loading spinner** while the metadata round-trip is in flight (it used to stay invisible until data arrived) **and a thumbnail preview** for image files; (3) the **icon-grid view gained a per-item overflow menu** (download · properties · rename · delete · pin) — those actions were reachable only in list view; (4) the **copy/move destination picker surfaces browse errors** instead of showing a silent empty folder; and (5) a hardcoded English `"Error: …"` status string is now localized across all 8 languages. (`FileTransferEngine.kt`, `FileTransferViewModel.kt`, `FileManagerSheets.kt`, `FileManagerFileItem.kt`, `FileTransferScreen.kt`, `FileManagerLogic.kt`, `strings.xml` ×9; RemEx-bi5z.)
- **Dashboard "Wake PC" now reports whether the packet actually sent.** The dashboard's Wake-on-LAN action optimistically showed "sent" regardless of the native result; it now parses the `WakePc` JNI response's success flag (mirroring the Remote Control screen) so a failed wake surfaces as a failure snackbar instead of a false confirmation. (`DashboardViewModel.kt`; RemEx-nbfb.)
- **The "PC found" snackbar no longer re-fires when you rotate the phone.** The discovery event was consumed only *after* its snackbar finished displaying (a few seconds), so a rotation in that window replayed it. The event is now consumed immediately on autofill and the snackbar runs on the screen's own scope, making it a true one-shot. (`ConnectionScreen.kt`; RemEx-b0lv.)

## [2.0.1] — 2026-07-11

### Added
- Remote desktop: **`encodedWidth`/`encodedHeight` on `desktop_meta` and `desktop_stream_descriptor`** — the true post-scale, even-aligned encoder output size, distinct from the existing `pixelWidth`/`pixelHeight` (unscaled screen size). The Android H.264 `SurfaceView` now sizes itself from these instead, and the host re-advertises them whenever the encoded size changes mid-stream (preset switch, adaptive-scale step). Additive, no `protocolVersion` bump; hosts predating the fields fall back to `pixelWidth`/`pixelHeight`. (`DesktopMeta`, `DesktopStreamDescriptor`, `RemoteDesktopHandler.GetEncodedFrameSize`.)
- Remote desktop: **adaptive H.264 capture scale** (RemEx-eo0f). A new pure, clock-injected state machine (`AdaptiveScaleController`) holds the sharpest capture scale the host can sustain at the target FPS instead of a fixed preset value — starting at the preset's configured scale and stepping up a coarse ladder (0.4/0.5/0.65/0.75/0.85/1.0) when the encoder proves it can keep up (≥98% of target FPS for 5 consecutive ~2s windows with no output drops), stepping straight back down on any encoded-output overflow or two consecutive windows under 90% of target FPS. 5s minimum between changes; a step-up that fails within its own hold period is barred from retrying for 60s (anti-oscillation). Opt-in via the new `DesktopConfig.AdaptiveScale` field (explicit client value wins; default is on for H.264 at `targetFps >= 90`). Android's SMOOTH_SHARP and UNLIMITED presets opt in explicitly; BALANCED/DATA_SAVER/CUSTOM defer to the host's default rule. (`AdaptiveScaleController`, `IH264Encoder.AcceptedInputFrameCount`/`DroppedAccessUnitCount`, `RemoteDesktopHandler`, `RemoteDesktopViewModel.buildConfigJson`.)
- Remote desktop, Android: **always advertise cursor-state/shape/frame-envelope capabilities**, independent of display-target selection — previously the client only sent `clientCapabilities` at all once a display option was resolved, so a fresh connection with no display picker interaction fell back to the legacy fixed-arrow cursor path. `supportsDisplaySelection` (and the paired `desktopProtocolVersion`/`captureMode`) stay gated on a resolved catalog option, since the host rejects an unpaired `SupportsDisplaySelection` advertisement. (`RemoteDesktopViewModel.buildConfigJson`.)

- Build: **`dotnet build`/`dotnet test Remex.sln` failed with XA5300 ("Android SDK directory could not be found") on any machine without the Android SDK configured**, because `remex.core.csproj` unconditionally multi-targeted `net10.0-android` alongside `net10.0`. `net10.0-android` is now only included in `TargetFrameworks` when `ANDROID_HOME`, `ANDROID_SDK_ROOT`, or an explicit `AndroidSdkDirectory` MSBuild property is set (mirroring how `build-remex.ps1` already resolves the SDK dir) — plain solution builds/tests now succeed without Android tooling installed, while `build-remex.ps1`'s Android build path (which always has one of those set) is unaffected. Added a COM fallback (`IGraphicsCaptureSession2::put_IsCursorCaptureEnabled`) for projection versions where the setter throws, and a Warning-level log (not Debug) when both paths fail so the doubled cursor is diagnosable from the host log. - Remote desktop, Android: **stream stayed cropped until a fullscreen toggle (or other unrelated re-layout) forced a rebuild.** The H.264 `SurfaceView`'s buffer→view content scale freezes at surface creation; if the surface was first created before real desktop metadata arrived (at the 1920×1080 placeholder) or before the encoded size was known, it stayed mis-scaled until something else happened to force a `key()` rebuild. Surface creation is now gated on `desktopMetaReady`, and the surface sizes itself from the new `encodedWidth`/`encodedHeight` fields instead of the unscaled `pixelWidth`/`pixelHeight`. (`RemoteDesktopScreen`.)
- Remote desktop, Windows: **macroblocking/blur on high-motion frames at high FPS.** The H.264 encoders (NVENC/QSV/AMF/x264) ran pure constant-QP with no `-maxrate`/`-bufsize` anywhere, so bitrate scaled unbounded with FPS×motion; when it overran the bounded encoded-output channel, `DropOldest` silently evicted access units mid-GOP, corrupting the reference chain until the next keyframe. Rate control is now quality-anchored VBR/QVBR with a QP-derived `-maxrate`/`-bufsize` ceiling (`FFmpegH264Encoder.ComputeMaxRateBps`/`ComputeBufSizeBps`), GOP now scales with FPS (`ComputeGop`, clamped 30–120) instead of a fixed 60, and output-channel overflow is now detectable (`DropWrite`) and recovers cleanly by dropping until the next IDR and requesting one, instead of forwarding a broken reference chain. VA-API (Linux) keeps its existing CQP rate control pending separate driver validation. (`FFmpegH264Encoder`.)
- Remote desktop, Windows: **cursor shape change (e.g. arrow → I-beam) took up to ~111ms to reach the client.** Shape re-sync previously only ran on the 10Hz "slow tick" alongside position streaming. The host now cheaply polls the current cursor handle (`WindowsCursorShapeCapture.TryGetCursorHandle`) on every 90Hz position tick and re-syncs immediately on a handle change, cutting worst-case shape-change latency to ~11ms; the 10Hz tick still runs unconditionally to catch animated cursors that mutate pixels without changing their handle.

### Changed
- Remote desktop, Windows: encoded-output overflow (`FFmpegH264Encoder`'s bounded output channel) no longer silently corrupts the stream on eviction — see Fixed above. This is a behavior change worth calling out separately: a sustained overflow now produces a brief freeze (bounded by one GOP) followed by a clean keyframe recovery, instead of macroblocking that could persist until the next natural GOP boundary.

- Remote desktop, Windows: the per-frame capture→encode conversion **no longer routes through `System.Drawing`/GDI+ on the hot path** — the real cause of a ~30 FPS ceiling that hardware NVENC was wrongly blamed for. Every capture backend (WGC/DXGI/GDI) previously wrapped each frame in `System.Drawing.Bitmap` objects and ran a GDI+ `Graphics.DrawImage` software blit, then a separate `LockBits`+`Marshal.Copy` into a fresh multi-MB `byte[]` — every frame. The downscale path (`scale < 1`) keeps GDI+'s native bilinear resampler (a scalar managed bilinear would be slower); GPU-side scaling is a measured follow-up. **For maximum FPS on a capable GPU, capture at full resolution (`scale 1.0`) and let the phone downscale for display** (NVENC handles full res easily; the new fit-to-height framing downscales on the phone). The end-to-end path required new JNI callbacks (`onDesktopCursorState`/`onDesktopCursorShape`) across the NativeAOT boundary. Legacy hosts/clients fall back to the generic-arrow overlay.
- Android build: the Gradle native-library sync and verify tasks (`syncRemexCore{Debug,Release}So`, `verifyRemexCoreIn{Debug,Release}Apk`) now locate `libRemexCore.so` under the repo-wide `artifacts/` output layout in addition to the legacy per-project `bin/` layout. Since `Directory.Build.props` enables `UseArtifactsOutput`, the NativeAOT output moved to `artifacts/bin/remex.core/<config>_net10.0-android_android-arm64/native/`, which the hardcoded `bin/` paths could no longer find — causing `Published Release libRemexCore.so not found` and a failed Android build even though the `.so` built successfully.
- Android build: `verifyRemexCoreIn{Debug,Release}Apk` no longer fails task-property validation on a fresh/clean build. The `apkDirectory` property was annotated `@InputDirectory`, which forced Gradle to require `build/outputs/apk/<variant>` to exist before the producing `assemble<Variant>` dependency had run, erroring with `directory ... doesn't exist`. It is now `@Internal` (the directory is produced by a dependency and the task has no outputs, so it is validated at execution time instead).
- Native JNI boundary: a **pending Java exception is now cleared before any further JNI call** at the managed↔unmanaged export boundary, and the export error path is fully non-throwing (degrade to a pre-serialized constant / `IntPtr.Zero`), preventing `SIGABRT` / NativeAOT-runtime aborts of the Android app when a marshalling call such as `GetStringChars` faults. (`JniHelper.ReadJString`, `AndroidNativeExports.Export`.) (JNI-1 RemEx-e3z, JNI-2 RemEx-9m1)
- Remote desktop: a **stalled hardware encoder or slow client no longer freezes the whole stream**. The host encoder's blocking stdin write on the capture thread is replaced with a bounded drop-frame `Channel` feeding a dedicated async writer that observes cancellation, so disconnect tears the writer down promptly and back-pressure drops frames instead of hanging. (`FFmpegH264Encoder`, `RemoteDesktopHandler`.) (RD-1 RemEx-ii3)
- Remote desktop: **unbounded encoder memory growth** when the consumer falls behind is fixed — the encoded-frame queue is a bounded drop-oldest `Channel` and the Annex-B accumulator is capped (reset past 8 MB without an AUD cut, guarding against malformed/desynced input). (`FFmpegH264Encoder`.) (RD-3 RemEx-fs5)
- Remote desktop: the ffmpeg **stderr reader is cancelled and torn down with the encoder**, so it can no longer touch a disposed logger/process or accumulate orphaned reader tasks during encoder-rebuild churn (e.g. dragging the quality slider). (`FFmpegH264Encoder`.) (RD-4 RemEx-aa0)
- Remote desktop: **dropped decoder input frames no longer cause ~1 s of green corruption**, and a desynced decoder recovers. The Android decoder uses `MediaCodec` async-callback mode with a bounded input queue (no silent drops) and requests a fresh keyframe on error/desync; the host implements **real on-demand IDR** (encoder reinit with forced-IDR codec flags) in place of the previous no-op. (`H264StreamDecoder`, `RemoteDesktopViewModel`, `FFmpegH264Encoder`, `RemoteDesktopHandler`.) (RD-2 RemEx-bqc)
- Remote desktop: a **mid-stream host resolution change no longer garbles the picture** — the Android decoder is (re)created from the host-reported pixel dimensions in frame meta (authoritative after the 4096 clamp) and handles `INFO_OUTPUT_FORMAT_CHANGED` / SPS-PPS-on-IDR reconfiguration. (`H264StreamDecoder`, `RemoteDesktopViewModel`.) (RD-5 RemEx-kx4)
- Discovery: **overlapping NSD resolves no longer fail with `FAILURE_ALREADY_ACTIVE`** or leak a pending resolve — the Android resolver serializes resolves with a mutex and is cancellable on both phases (pre-API-34), fixing the race between manual discovery and reconnect self-heal. (`NsdDiscoveryManager`.) (NSD-1 RemEx-a13)
- Discovery: the host **re-advertises mDNS on network change** (DHCP renew / NIC switch / VPN up-down) instead of advertising once at startup, and **advertises on all preferred interfaces** with Linux-aware virtual-interface filtering (`docker`/`virbr`/`tailscale`/`wg`/`veth`), so multi-NIC and Linux hosts stay discoverable on the client's segment. (`MdnsAdvertisingService`.) (NSD-4 RemEx-ngs, NSD-5 RemEx-i8x)
- Local IPC is now a **length-prefixed framed protocol** (4-byte big-endian length, 1 MB cap) shared by the server and every client, so payloads over 8192 bytes and chunked writes parse correctly and oversize frames are rejected before allocation. (`RemExLocalIPC`, `LocalIpcServerService`, IPC clients.) (IPC-3 RemEx-4ic)
- Protocol-version acceptance is now a **single shared policy** (`ProtocolVersionPolicy`) applied consistently to `/ws` and `/ws/desktop`, replacing two divergent ad-hoc checks (`< 2` vs `!= "2"`). (`ProtocolVersionPolicy`, `PingPongHandler`, `HostBootstrapper`.) (PROTO-4 RemEx-4uy)
- Native JNI pairing exports are now **race-free and exception-safe**. `StartPairingNative`/`SubmitPairingPinNative` serialize all transitions of the pairing-session statics under a dedicated lock (kept separate from the high-frequency frame/callback lock) so a concurrent call from a second Java thread can no longer dispose-then-use the active `ClientWebSocket` (`ObjectDisposedException`); their jstring marshalling now runs inside the export boundary guard so a managed throw is caught instead of escaping `[UnmanagedCallersOnly]`; and the frame/string callback paths clear any pending Java exception on an allocation-failure early return so it can't bleed into the next callback on the shared dispatcher env. (`AndroidNativeExports`.) (JNI-4 RemEx-8ay, JNI-5 RemEx-85i, JNI-3 RemEx-ymb)
- Local IPC server: the backoff `Task.Delay` calls in the accept-loop catch blocks are now cancellation-guarded, so service shutdown exits the loop cleanly instead of surfacing a cancelled task from `ExecuteAsync`. (`LocalIpcServerService`.) (IPC-7 RemEx-79h)
- Local IPC client: an **ACL denial is now distinguished from "no server running"** — `RemExLocalIPC.SendCommandAsync` returns a typed permission error (and the legacy PIN query emits a diagnostic naming the exception type) instead of collapsing every failure into a generic `IPC Error`/`null`, so the UI can surface an actionable message. (`RemExLocalIPC`, `IpcPairingPinQueryService`.) (IPC-8 RemEx-b3m)
- Discovery: `ConnectionViewModel.discoverHost()` now **cancels any in-flight discovery before relaunching** (cancel-previous via a tracked `Job`), so overlapping manual + self-heal calls no longer stack NSD resolves or multicast-lock cycles. (`ConnectionViewModel`.) (NSD-3 RemEx-4bb)
- The loopback gate on `GET /pairing-pin` / `POST /start-pairing` now treats a **null `RemoteIpAddress` as non-loopback** (reject with `404`) instead of throwing `ArgumentNullException` inside the handler. (`HostBootstrapper`.) (PAIR-5 follow-up)
- Android build: the Gradle `.so` sync now **rejects a non-AArch64 / non-ELF `libRemexCore.so`** before it is packaged (validates the ELF magic, 64-bit class, and `EM_AARCH64` machine), restricts candidates to the requested configuration with case-insensitive path matching, and tracks the published `.so` as a **content-hashed task input** so an `-NoClean` build re-syncs when the library changes instead of staying `UP-TO-DATE` and packaging a stale `.so`. (`build.gradle.kts`.) (JNI-6 RemEx-hht, RemEx-l79)
- Remote desktop: the on-demand keyframe-request wire type is now the shared typed Core constant `MessageTypes.DesktopKeyframeRequest` instead of a stray host-local literal. (`RemexMessage`, `RemoteDesktopHandler`.) (RemEx-kjq)

### Security
- Pairing endpoints **gated to loopback** (PAIR-5, RemEx-a75): `GET /pairing-pin` and `POST /start-pairing` now reject any non-loopback caller with a `404` (not advertising the endpoint). Previously these disclosed the active pairing PIN — the out-of-band pairing secret — to unauthenticated remote callers, enabling remote takeover. The host tray reads the PIN over local IPC, not HTTP. (`HostBootstrapper`.)
- **PIN brute-force throttle** (PAIR-2, RemEx-lhd): the PIN verification path now counts failed attempts per session and burns the session (forcing a brand-new PIN) after 5 mismatches, the pairing session lifetime is cut from 10 minutes to 2 minutes, and a per-IP sliding-window throttle (`PairingThrottle`) bounds repeated `/start-pairing` attempts. Closes the online-grinding window against a 6-digit PIN. (`PairingService`, `PairingThrottle`, `HostBootstrapper`.)
- **Reconnect proof-of-possession** (PAIR-1, RemEx-3n6): a persisted `clientId` is no longer a bearer credential. At pairing completion the host binds each client to a 32-byte reconnect secret (the ECDH/HKDF session key) in `PairedClientRegistry`; on every reconnect the host sends a random nonce and requires `HMAC-SHA256(secret, nonce)` back, verified with `CryptographicOperations.FixedTimeEquals`, before trusting the connection. Replaying a captured `clientId` without the secret now fails. Added as **new optional handshake messages** (`reconnect_challenge` / `reconnect_proof`) — **no `protocolVersion` bump**; legacy secret-less clients are challenged and must re-pair. Requires a coordinated Android + Host release. (`PairedClientRegistry`, `PairingService`, `PairingHandler`, `PingPongHandler`, Core `PairingClient`/`RemexNativeClient`, `RemexMessage`/`PairingMessages`.)
- **Hardened `paired_clients.json` permissions** (PAIR-4, RemEx-rc4): the registry store now holds reconnect secrets, so after every write it is locked to the service identity only — Unix `0600` (owner read/write) on Linux/macOS and an ACL granting only LocalSystem + Administrators (inheritance disabled) on Windows. (`PairedClientRegistry`.)
- **Authenticated 8338 command channel** (PROTO-1, RemEx-htt): the external TCP command port — which executes shutdown/restart/sleep/lock — previously dispatched after a *server-only* TLS handshake with **zero client authentication**, so any device on the network could power-control the PC. Commands now carry a paired-client `ClientId` validated against `PairedClientRegistry` before dispatch (default-deny, mirroring the `/ws` gate); unauthenticated callers get `Unauthorized` and the connection closes, and the channel **fails closed** when no authenticator is registered. The listener stays bound to all interfaces by design (authenticated-remote — the Session-0 service must serve commands with no user logged in). (`RemexNetworkListener`, `ICommandChannelAuthenticator`, `PairedClientChannelAuthenticator`, `CommandRequest.ClientId`.)
- **8338 flood / slow-loris bounds** (PROTO-2, RemEx-4ky): the command listener caps concurrent connections via a configurable `SemaphoreSlim` (`Remex:CommandMaxConcurrent`, default 16, reject-at-capacity) and applies handshake/read timeouts (`Remex:CommandHandshakeTimeoutSeconds` / `CommandReadTimeoutSeconds`) through linked `CancellationTokenSource`s, so a slow or idle peer can no longer wedge the channel or multiply `MaxPayloadSize` allocations. (`RemexNetworkListener`.)
- **Oversize `/ws` message no longer leaks connection state** (PROTO-3, RemEx-288): a frame exceeding the 4 MB cap previously threw an uncaught `InvalidOperationException` that bypassed cleanup, orphaning the telemetry stream task and leaking file-transfer/pairing state. The serializer drains and returns null on oversize, and the handler's cleanup now runs in a `finally`. (`MessageSerializer`, `PingPongHandler`.)
- **Host private key no longer world-readable** (PAIR-3, RemEx-dta): the TLS PFX is written atomically with restrictive permissions set **before** any key bytes touch disk (Unix `0600`; Windows ACL: LocalSystem + Administrators), closing the TOCTOU window in which a non-admin local user could read the SPKI-pinned private key. (`CertificateService`.)
- **Local IPC pipe locked down + caller verified** (IPC-1, RemEx-m1i): the live `RemExLocalIPC` pipe granted **Everyone** read/write and returned the active pairing PIN (and accepted power commands) to any local user. The `Everyone` ACE is removed — the pipe grants only LocalSystem (FullControl) + Interactive (ReadWrite) on Windows (`0600` owner-only on Linux) — and secret-returning/state-changing commands additionally verify the connected client is the interactive console user via pipe impersonation. (`LocalIpcServerService`.)
- **Bounded IPC accept loop** (IPC-2, RemEx-n6u): the IPC server handles each client on its own task and re-accepts immediately, with a per-connection read timeout, so a hung/silent local client can no longer wedge the PIN/power channel. (`LocalIpcServerService`.)
- **Explicit ACL on the host-control handoff pipe** (IPC-6, RemEx-oj8): the `RemExHostControl` port-handoff pipe carries an explicit DACL (LocalSystem FullControl + Interactive ReadWrite on Windows; Unix perms on Linux) instead of the default — the Session-0 service (LocalSystem) and the HIGH-integrity interactive GUI host run in different security contexts, so this meaningfully tightens the handoff. (`HostControlServer`.)
- **Pairing acknowledgement HMAC compared as raw bytes** (PAIR-6, RemEx-29e): the host now decodes the client's acknowledgement HMAC from base64 and compares the raw fixed-length bytes with `CryptographicOperations.FixedTimeEquals`, failing closed on malformed base64 — instead of comparing the base64 *text* (encoding artifacts) and risking a throw out of the verify path. Mirrors the client side. (`PairingService`.)
- **No crypto/exception detail leaked to the pairing peer** (PAIR-7, RemEx-xk9): a malformed client ECDH key (or any failure on the pairing-complete path) now returns a generic error to the peer — the wrong-PIN message on the complete path so a crypto/parse error is indistinguishable from a bad PIN — with full detail logged host-side only, instead of interpolating `ex.Message` into the peer-facing error. (`PairingHandler`.)
- **Untrusted pointer samples clamped before integer cast** (RD-8, RemEx-q6u): incoming `DesktopPointerSample` coordinates/deltas (network-supplied floats) are validated through a new `CoordinateValidation` helper — non-finite values (NaN/±Infinity) are rejected and values are clamped to the active stream pixel bounds — before the `(int)` cast, so a hostile sample can no longer wrap into an arbitrary `MoveMouse` coordinate. (`CoordinateValidation`, `RemoteDesktopHandler`.)
- **mDNS-discovered host fields validated before URL build** (NSD-6, RemEx-00x): `MdnsDiscoveryService` now rejects an invalid SRV port and a target that isn't a valid IP/DNS name (`Uri.CheckHostName`) before composing the `ws://` URL from untrusted multicast responder data. (`MdnsDiscoveryService`.)
- **8338 `ClientId` requirement documented for external scripts** (PROTO-1 follow-up, RemEx-lbk): `docs/API_CONTRACTS.md` §4 and `docs/SECURITY.md` now accurately describe that every external-script `CommandRequest` on port 8338 must carry a paired `ClientId` (default-deny; unauthenticated senders get `Unauthorized`), replacing the prior inaccurate "same-IP within 24h" description. No first-party client uses 8338, so this is a documentation/integration concern only.
