# RemEx 2.0 "Cosmic Raven" — Final Pre-Polish Audit Report

**Auditor:** Claude Code (Sonnet 4.6 + Opus Advisor)  
**Date:** 2026-05-09  
**Branch:** `2.0`  
**Verdict:** NOT READY FOR POLISH PHASE — 4 Critical Blockers must be resolved first

---

## 1. Executive Summary

This report is the result of a full microscopic audit of the RemEx 2.0 codebase conducted against the master plan, the 2.0-Tracker, and current Android/platform best practices. Every source file, manifest entry, dependency declaration, and architectural contract was examined.

The overall engineering quality is high. The TLS foundation, certificate SPKI pinning, EncryptedSharedPreferences storage, R8 shrinking rules, network security config, foreground service type, file transfer path traversal protection, and coroutine architecture are all done correctly. The codebase is close to ready.

However, four blockers prevent entry into the polish phase. Two are security issues that would pass QA but expose production users to real attack vectors. Two are scope control failures where committed code violates explicit locked decisions in the master plan.

## 2. Critical Blockers

### BLOCKER-1: No Post-Pairing Authorization Gate on WebSocket Commands

**Files:** `Remex.Host/Handlers/PingPongHandler.cs` (case MessageTypes.Command, lines ~121–128)  
**Severity:** Critical / Security

The `PingPongHandler` dispatches every incoming command — including `Shutdown`, `Restart`, `HibernatePC`, `Sleep`, `MonitorOff`, and file transfer operations — without verifying that the connecting client has successfully completed the pairing flow. Any client that establishes a TLS connection (even with an unrecognized self-signed certificate, see BLOCKER-2) can immediately issue destructive host OS commands.

The `PairingService` does expose state indicating whether pairing is complete, but that state is never consulted in the command dispatch path. The tracker notes "pairing verification deferred to later track" in `RemexNetworkListener.cs` (line ~280), but no subsequent track ever closed this gap. This is not a theoretical risk — the WebSocket endpoint is reachable from any device on the same network the moment the host is running.

**Required fix:** The handler must reject all `Command`, `FileTransferRequest`, and related message types unless the connection has a verified `isPaired` session flag. The flag must be set per-connection (not as singleton PairingService state) and must be checked before dispatch.

### BLOCKER-2: `AcceptSelfSignedCertificate` Always Returns `true` for Unknown Certificates

**File:** `Remex.Client/ViewModels/ConnectionViewModel.cs` (lines ~1051–1079, method `AcceptSelfSignedCertificate`)  
**Severity:** Critical / Security

During TLS handshake validation, the client checks incoming certificate SPKI hashes against its pinned store. If the hash is **not found** in the store — which is exactly the condition during a man-in-the-middle attack using a different self-signed certificate — the method logs a warning and then returns `true`, accepting the certificate unconditionally.

This means that on first connection, or any time the pin store is empty or the host cert has changed, a MITM attacker with their own self-signed certificate is fully accepted. The pinning logic exists but is bypassed on the miss path. The entire security model depends on this check being strict.

A secondary defect on line ~1067: `store.GetAllPinsAsync().GetAwaiter().GetResult()` is a blocking async call inside a TLS validation callback. This will deadlock on certain synchronization contexts.

**Required fix:** Return `false` (reject) for any certificate whose SPKI hash is not present in the pin store. A separate "first-time trust" UX flow (e.g., show the hash to the user for manual confirmation) is required for the initial connection. This is described in the master plan but was not implemented.

### BLOCKER-3: Five Unauthorized Quick Settings Tile Services Committed

**Files (untracked `??`):**
- `RemEx.Android/app/src/main/java/com/clindsay94/remex/tile/RemexHibernateTileService.kt`
- `RemEx.Android/app/src/main/java/com/clindsay94/remex/tile/RemexMonitorOffTileService.kt`
- `RemEx.Android/app/src/main/java/com/clindsay94/remex/tile/RemexRestartTileService.kt`
- `RemEx.Android/app/src/main/java/com/clindsay94/remex/tile/RemexShutdownTileService.kt`
- `RemEx.Android/app/src/main/java/com/clindsay94/remex/tile/RemexSleepTileService.kt`

**Files (tracked, modified):** `RemEx.Android/app/src/main/AndroidManifest.xml` (service declarations for all five)  
**Severity:** Critical / Scope Violation

The master plan, §1 (Explicit Out-of-Scope decisions), states: *"Mute Audio Quick Settings tile — ship 'Lock PC' tile only."* Track 2I in the tracker confirms: *"RemexLockTileService + BIND_QUICK_SETTINGS_TILE manifest entry + ic_lock drawable."* Exactly one tile service was authorized.

Five additional tile services have been created and registered in the manifest, none of which were authorized. These are untracked files whose manifest entries have been staged into tracked manifest modifications. This compounds BLOCKER-4 below: all five services dispatch destructive host OS commands with no `unlockAndRun {}` wrapper, meaning Hibernate, Shutdown, Restart, Sleep, and MonitorOff can all be triggered from a locked device screen without user authentication.

**Required fix (option A):** Remove all five unauthorized tile service files and their corresponding manifest entries, strings, and drawables. Keep only `RemexLockTileService`. This is the correct path for 2.0.

**Required fix (option B):** If the decision is made to include these tiles in 2.0 scope, the master plan and tracker must be formally updated to reflect the expanded scope, and each tile service must be corrected for BLOCKER-4 first.

### BLOCKER-4: All Six Tile Services Execute Without `unlockAndRun {}` Wrapper

**Files:**
- `RemEx.Android/app/src/main/java/com/clindsay94/remex/tile/RemexLockTileService.kt`
- All five files listed in BLOCKER-3

**Severity:** Critical / Security

Android's `TileService` exposes the `onClick()` handler even when the device screen is locked. The OS provides `TileService.unlockAndRun {}` for exactly this scenario: it prompts the user to unlock the device before executing the callback. None of the six tile services use this mechanism.

As a result, a physical attacker who picks up a locked Android device can pull down the Quick Settings shade and trigger Shutdown, Restart, Sleep, Hibernate, or MonitorOff on the connected remote PC without any authentication challenge on either the Android device or the host. For the Lock PC tile this is lower-risk (locking an already-locked PC), but the remaining five actions are destructive and completely unprotected.

**Required fix:** Wrap all `onClick()` implementations in `TileService.unlockAndRun { ... }`. All destructive actions must be inside the lambda so they only execute after the user authenticates.

## 3. High-Priority Issues

### HIGH-1: NSec.Cryptography (X25519) Never Added to Csproj — Tracker Integrity Failure

**Files:** `Remex.Host/Remex.Host.csproj`, `Remex.Core/Remex.Core.csproj`, `Remex.Host/Services/Security/PairingService.cs`, `Remex.Core/Native/PairingClient.cs`  
**Severity:** High / Plan Compliance + Tracker Integrity

The master plan and tracker both explicitly specify pairing uses *"ECDH X25519 via NSec.Cryptography 22.4.0."* The tracker's issues log records an incident (2026-05-04) where the Android client was upgraded to match the host's X25519 implementation.

Neither `NSec.Cryptography` nor any X25519-providing package appears in either `.csproj` file. Grep of the entire solution returns no results for `NSec`. The actual implementation in both `PairingService.cs` and `PairingClient.cs` uses `ECCurve.NamedCurves.nistP256` (P-256) via the built-in .NET `ECDiffieHellman` API.

P-256 is cryptographically sound and this works correctly at runtime. However:

1. The tracker falsely claims a specific library was used. This is a tracker integrity failure.
2. If any future agent or developer relies on the tracker's accuracy (as intended), they will have a wrong understanding of the cryptographic dependencies.
3. The issues log entry (2026-05-04) specifically says the fix was to use NSec/X25519 — but the code does not reflect this.

**Required fix:** Either add the NSec.Cryptography package and migrate to X25519 as specified, OR formally update the master plan and tracker to document that P-256 via the built-in .NET API was chosen instead, with the rationale. The current state (plan says one thing, code does another, tracker confirms the lie) is unacceptable in a production audit trail.

### HIGH-2: `PairingService` Singleton Has Single-Session State — Concurrent Pairing Corrupts State

**File:** `Remex.Host/Services/Security/PairingService.cs`  
**Severity:** High / Thread Safety

`PairingService` is registered as a singleton in `HostBootstrapper`. Its pairing-session state — `_activePin`, `_hostEcdh`, `_sessionKey`, `_sharedSecret`, `_clientPublicKeyBase64` — is all stored as instance-level fields. If two clients initiate pairing simultaneously, both are modifying the same fields. One session's ECDH key pair will overwrite the other's, producing an authentication failure for one client and potentially producing a session key derived from mismatched material.

In practice this is unlikely in the intended single-host single-device use case, but it is a correctness bug.

**Required fix:** Convert pairing state to per-connection scope. Either use a `ConcurrentDictionary` keyed by connection ID, or enforce that only one pairing session is active at a time via a semaphore that rejects concurrent requests.

### HIGH-3: `RemexNetworkListener` Falls Back to Plaintext TCP on Certificate Load Failure

**File:** `Remex.Core/Services/Network/RemexNetworkListener.cs` (lines ~234–238)  
**Severity:** High / Security Regression

When the TLS certificate cannot be loaded (file missing, parse failure, permissions error), the listener logs a warning and continues to accept plaintext TCP connections instead of refusing to start. This silently downgrades the entire security model to pre-2.0 state: no encryption, no pairing, plaintext commands on the wire.

Given that the entire purpose of the 2.0 security backbone (Tracks 1A–1E) is to eliminate exactly this scenario, a silent plaintext fallback is unacceptable.

**Required fix:** On certificate load failure, throw an exception or call `Environment.Exit(1)` with a clear error message. The host must never accept connections without TLS.

---

### HIGH-4: `RemexNativeClient.HandleMessage` Command Correlation Is Broken

**File:** `Remex.Core/Native/RemexNativeClient.cs` (lines ~275–283)  
**Severity:** High / Correctness

`SendCommandAsync` generates a correlation ID via `Interlocked.Increment` and stores a `TaskCompletionSource` in a pending-commands dictionary keyed by that ID. However, the correlation ID is never serialized into the outgoing message's `CorrelationId` field. The host therefore never knows which ID to echo back. On the receive side, response matching takes the first pending TCS rather than matching by ID.

Under concurrent command dispatch — which happens during file operations and the command pipeline — this produces response misrouting: command A's response resolves command B's Task. The bug is silent in happy-path single-command scenarios, which is why it passed testing.

**Required fix:** Set `CorrelationId` on the outgoing message object before serializing. Ensure the host echoes the `CorrelationId` in the response. The receive-side match must look up by ID, not by insertion order.

### HIGH-5: `ACCESS_LOCAL_NETWORK` Runtime Permission Flow Not Implemented (Android 17 / SDK 37)

**File:** `RemEx.Android/app/src/main/AndroidManifest.xml` (line 14), `RemEx.Android/app/build.gradle.kts` (`targetSdk = 37`)  
**Severity:** High / Functionality on Android 17

The manifest declares `android.permission.ACCESS_LOCAL_NETWORK`. On Android 17 (API 37), this permission requires a runtime prompt — declaring it in the manifest is not sufficient. The 2.0-Tracker's 2D notes acknowledge this: *"TargetSdk 37 follow-up remains outside the original checklist: local-network permission flow + Android 17 LAN regression pass."*

If this is not resolved before release, the app will silently fail to connect to any host on Android 17 devices without any user-facing error explaining why. Given that `targetSdk = 37` is set, this is not a hypothetical future concern.

**Required fix:** Implement the runtime permission request for `ACCESS_LOCAL_NETWORK` at connection time, with a rationale string explaining why LAN access is needed. Handle the denial case with a user-facing error. This work item is already acknowledged in the tracker but must move from "outside the checklist" to a tracked task before polish.

## 4. Medium and Low Priority Issues

### MED-1: `HostBootstrapper` Double-Instantiates `CertificateService`

**File:** `Remex.Host/HostBootstrapper.cs` (lines ~86–88 and ~117–124)  
**Severity:** Medium / Code Quality

`CertificateService` is registered with the DI container at line ~87, then manually instantiated again at line ~117, where `GetAwaiter().GetResult()` blocks synchronously during startup. The second instance is then re-registered as a singleton, overwriting the first DI registration. This means the DI-resolved `ICertificateService` and the `CertificateService` used during bootstrap initialization are different instances until the override. This is fragile and will be a maintenance trap.

**Required fix:** Use a single `AddSingleton` registration with an async-factory or resolve the service from the container after the host is built, calling the initialization method before accepting connections.

---

### MED-2: `PingPongHandler` Never Validates `ProtocolVersion`

**File:** `Remex.Host/Handlers/PingPongHandler.cs`  
**Severity:** Medium / Protocol Correctness

The master plan specifies that the host must reject connections where `ProtocolVersion < 2`. No such check exists anywhere in the message dispatch chain. A 1.x client can connect, handshake, and issue commands without being rejected. During the 2.0 rollout period, old clients should get a clear rejection rather than silently operating in a degraded or unpredictable state.

**Required fix:** After the initial handshake message, check `ProtocolVersion`. If less than 2, send an error response with a minimum-version message and close the WebSocket.

---

### MED-3: `ic_hibernate.xml` Drawable Uses Wrong Icon (Login Arrow, Not Hibernate)

**File:** `RemEx.Android/app/src/main/res/drawable/ic_hibernate.xml`  
**Severity:** Medium / UX

The vector path data in `ic_hibernate.xml` renders as a right-pointing arrow with a vertical bar (a login/enter icon, similar to Material's `login` or `exit_to_app`). It does not represent hibernation visually. The Quick Settings tile labeled "Hibernate" will show a login arrow icon to users.

The `ic_monitor_off.xml` path data (monitor with diagonal slash) is correct. Only `ic_hibernate.xml` is wrong.

**Required fix:** Replace the path data with a hibernation-appropriate icon (snowflake, `power_settings_new` with a Z, or similar — Material Design's `bedtime` or a custom snowflake path would be appropriate).

---

### MED-4: `FileTransferHandler.StreamDownloadAsync` Is Fire-and-Forget

**File:** `Remex.Host/Handlers/FileTransferHandler.cs` (line ~145)  
**Severity:** Medium / Error Handling

`_ = StreamDownloadAsync(state, ws, ct)` discards the returned Task. If `StreamDownloadAsync` throws an unhandled exception, it is silently swallowed. This means a failed download leaves the client waiting for a `FileTransferEnd` message that never arrives, and the server has no record of the failure.

**Required fix:** Await the task within a try-catch, or use `Task.Run` with proper exception propagation. Log and surface failures through the normal error-response path.

---

### MED-5: `FileTransferService.LoadConfiguredRoots()` Swallows All Exceptions Silently

**File:** `Remex.Host/Services/FileTransfer/FileTransferService.cs`  
**Severity:** Medium / Observability

The `LoadConfiguredRoots()` method contains a bare `catch {}` block that swallows all exceptions without logging. A corrupted configuration file, a missing environment variable, or a deserialization error will produce zero diagnostic output. The service will start with an empty root set, and users will get "no shared folders configured" errors with no way to diagnose why.

**Required fix:** Replace the bare catch with a logged catch: at minimum `_logger.LogError(ex, "Failed to load configured roots")`. Do not rethrow — empty roots is a recoverable state — but do log.

---

### LOW-1: `PinnedCertStore.EnsureLoaded()` Uses Blocking `_lock.Wait()`

**File:** Referenced in `RemexNetworkListener.cs`  
**Severity:** Low / Thread Safety

`EnsureLoaded()` uses a synchronous `SemaphoreSlim.Wait()` call. In an async context (which all callers are), this blocks the calling thread. Under normal usage this is fast enough that it will not manifest as a visible bug, but it violates the async-all-the-way principle and could cause thread starvation under high load.

**Required fix:** Change to `await _lock.WaitAsync()` and make `EnsureLoaded` async.

---

### LOW-2: `RemexNativeClient.Dispose()` Blocks on Async via `GetAwaiter().GetResult()`

**File:** `Remex.Core/Native/RemexNativeClient.cs`  
**Severity:** Low / Code Quality

`Dispose()` calls `DisconnectAsync().GetAwaiter().GetResult()`. This is a well-known anti-pattern: calling `.GetAwaiter().GetResult()` inside a `Dispose()` method risks deadlocking on certain synchronization contexts. The correct pattern is either to implement `IAsyncDisposable` and use `await using`, or to fire-and-forget the disconnect and clean up synchronous resources only in `Dispose()`.

---

### LOW-3: `android:allowBackup="true"` Deserves Explicit Acknowledgment

**File:** `RemEx.Android/app/src/main/AndroidManifest.xml` (line 23)  
**Severity:** Low / Risk Acknowledgment

`allowBackup="true"` is set. The `data_extraction_rules.xml` correctly excludes the SPKI pin store and DataStore preferences from backups. The Android KeyStore master key used by `EncryptedSharedPreferences` is not exportable by design. This combination is acceptable, but the configuration should be documented explicitly so future maintainers do not inadvertently add sensitive data to the backed-up set without updating the exclusion rules.

## 6. Recommended Handoff for Next Agent

**Before any polish work begins, resolve in this order:**

1. **BLOCKER-1 (Pairing gate):** Add a per-connection `isPaired` boolean to the WebSocket session context. Set it only in `PairingComplete` handler after successful ECDH verification. Gate all `Command` and `FileTransfer*` message types on this flag.

2. **BLOCKER-2 (AcceptSelfSignedCertificate):** Return `false` on hash-not-found. Implement a first-time-trust confirmation UX where the user sees and manually approves the SPKI hash before it is persisted. This is described in the master plan and is a required security feature, not optional polish.

3. **BLOCKER-3 (Unauthorized tiles):** Decide: remove the five tiles (recommended, 2.0-compliant) or formally expand scope. Either path requires updating the tracker. If removing, delete the five `.kt` files, their manifest entries, their string resources, and their drawables.

4. **BLOCKER-4 (unlockAndRun):** Wrap all tile `onClick()` handlers in `TileService.unlockAndRun {}` before anything ships, regardless of the BLOCKER-3 decision.

5. **HIGH-1 (NSec/tracker integrity):** Reconcile the tracker with reality. This is a one-sentence tracker update if P-256 is the correct implementation, or a dependency add if X25519 was genuinely intended.

6. **HIGH-3 (plaintext fallback):** Make certificate load failure fatal. One line change.

7. **HIGH-4 (correlation ID):** Set `CorrelationId` in outgoing command messages. One field assignment.

8. **HIGH-5 (Android 17 LAN permission):** Create a Track 3E or fold into 3D. Cannot ship targetSdk=37 without this.

Once the four blockers are cleared, the remaining HIGH items (HIGH-2 singleton pairing, HIGH-3, HIGH-4, HIGH-5) and MED items can be worked in any order during the polish phase.
